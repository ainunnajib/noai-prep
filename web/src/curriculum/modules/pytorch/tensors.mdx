Every number a PyTorch model touches (a pixel, a word embedding, a weight, the loss) lives inside a **tensor**. Most PyTorch bugs in the NOAI Final are not about clever maths: a tensor has the wrong shape, the wrong type, or an operation runs along the wrong axis. Many of these bugs never raise an error; they just give wrong answers. This lesson makes shapes something you can *see* and predict before you run anything.

You already know NumPy arrays (shape, `reshape`, `axis=`). PyTorch tensors work the same way, with two extra powers you will use in the next lessons: they can live on a GPU, and they can record the operations done to them so that gradients can be computed automatically.

<Analogy title="Boxes of mooncakes">

Mooncakes sit in a tray of 4, trays go into a carton, cartons go into a crate. Describe a crate by (cartons, trays, cakes) and you have a shape. Shape surgery is repacking: put one tray into its own carton so it fits on the shelf with the others (add an axis), throw away a carton that only holds one tray (remove an axis), or turn the crate so the cartons face a different way (reorder the axes). The cakes themselves never change; only the packaging does.

</Analogy>

## What a tensor is

A <Term def="PyTorch's multi-dimensional array: a grid of numbers of one type, with a shape. Like a NumPy array, but it can live on a GPU and can track gradients.">tensor</Term> is a grid of numbers of one type. The number of axes is called its rank or `ndim`, and the shape lists the length of each axis:

| Example | Shape | ndim |
|---|---|---|
| a loss value | `()` | 0 |
| scores for 10 classes | `(10,)` | 1 |
| a greyscale image, 28 × 28 pixels | `(28, 28)` | 2 |
| a colour image | `(3, 224, 224)` | 3 |
| a batch of 32 colour images | `(32, 3, 224, 224)` | 4 |

```python
import torch

x = torch.tensor([[1., 2., 3.],
                  [4., 5., 6.]])
print(x.shape)       # the size of each axis
print(x.ndim)        # how many axes
print(x.numel())     # how many numbers in total
print(x.dtype, x.device)
print(x[1, 2], x[:, 0])
```

```text
torch.Size([2, 3])
2
6
torch.float32 cpu
tensor(6.) tensor([1., 4.])
```

`torch.Size([2, 3])` behaves like the tuple `(2, 3)`. Indexing and slicing (`x[1, 2]`, `x[:, 0]`), arithmetic and broadcasting all follow the NumPy rules you already know.

## Creating tensors and predicting the dtype

Every tensor has one <Term def="Data type: the kind of number every element is stored as, such as int64 (whole numbers) or float32 (decimals with about 7 significant digits).">dtype</Term>. Two creation functions look almost the same but behave differently:

- **`torch.tensor(data)`** (lowercase) copies your data and *infers* the dtype from it: whole numbers give `int64`, any decimal gives `float32`, and `True`/`False` give `bool`.
- **`torch.Tensor(data)`** (capital T) is the tensor class itself. Calling it always gives `float32`, whatever you pass in.

Generators such as `torch.zeros(2, 3)`, `torch.ones`, `torch.rand` (uniform between 0 and 1), `torch.randn` (normal distribution) and `torch.linspace` give `float32`; `torch.arange(5)` with whole numbers gives `int64`. Notice one difference from NumPy: PyTorch's default float is **float32**, while NumPy's is float64.

```python
import torch
import numpy as np

print(torch.tensor([1, 2, 3]).dtype)       # whole numbers
print(torch.tensor([1, 2, 3.5]).dtype)     # one decimal is enough
print(torch.Tensor([1, 2, 3]).dtype)       # capital T: always float32
print(torch.arange(5))
print(torch.zeros(2, 3))
print(torch.from_numpy(np.array([0.5, 1.0])))   # keeps NumPy's float64
```

```text
torch.int64
torch.float32
torch.float32
tensor([0, 1, 2, 3, 4])
tensor([[0., 0., 0.],
        [0., 0., 0.]])
tensor([0.5000, 1.0000], dtype=torch.float64)
```

Why should you care? Try the combinations yourself:

<DtypeInspector />

Three rules come out of it:

1. **Element-wise arithmetic promotes.** `int64 + float32` gives `float32`, so `+`, `-`, `*` and `/` rarely complain.
2. **Matrix products and layers do not promote.** `@` and `nn.Linear` need *exactly* the same dtype on both sides. Feeding NumPy data (float64) or integer data into a model gives `mat1 and mat2 must have the same dtype`. The fix is `x.float()`, which converts to float32.
3. **Gradients need floating point.** `torch.tensor([1, 2], requires_grad=True)` fails, because you cannot nudge an integer by 0.001. (Class labels for a classification loss are the exception: they *should* be `int64`, because they are indices, not things you differentiate.)

<Mistake title="torch.Tensor(3) is not the number 3">

`torch.tensor(3)` is a 0-D tensor holding the number 3. `torch.Tensor(3)` reads the 3 as a *size* and gives three uninitialised float32 numbers, whatever happened to be in memory. Use lowercase `torch.tensor` for data.

</Mistake>

## Shape surgery

These tools rearrange a tensor without changing a single number. Use $(3, 4)$ as the running example:

- **`x.view(…)` / `x.reshape(…)`** regroup the numbers in reading order; one size may be `-1`, meaning "work it out": `x.reshape(2, -1)` gives `(2, 6)`.
- **`x.unsqueeze(d)`** inserts a new axis of size 1 at position `d`: `x.unsqueeze(0)` gives `(1, 3, 4)` and `x.unsqueeze(1)` gives `(3, 1, 4)`.
- **`x.squeeze(d)`** removes axis `d` if its size is 1, and **`x.squeeze()`** removes every size-1 axis: a `(1, 3, 1, 4)` tensor squeezes to `(3, 4)`.
- **`x.permute(…)`** puts the axes in a new order: `x.permute(1, 0)` gives `(4, 3)`.
- **`x.transpose(a, b)`** swaps two axes (`x.T` for 2-D): `x.transpose(0, 1)` gives `(4, 3)`.
- **`x.flatten(s)`** merges every axis from `s` to the end into one: `x.flatten()` gives `(12,)`.

The one that needs care is `permute`. Read `x.permute(2, 0, 1)` as "new axis 0 is old axis 2, new axis 1 is old axis 0, new axis 2 is old axis 1". So each argument is an *old position*, listed in the *new order*.

### Images are (N, C, H, W)

PyTorch's convolution layers expect a batch of images shaped **(N, C, H, W)**: **N** images in the batch, **C** colour channels (3 for RGB), then the height **H** and width **W** in pixels. Image files, NumPy and matplotlib store a single photo as **(H, W, C)** instead, with the three colour values of each pixel side by side. Converting between the two is the most common shape surgery in computer vision. Try it on a tiny 4 × 5 photo:

<TensorShapeLab />

<KeyIdea>

Shape operations never change the numbers, only how they are grouped and ordered. Say what each axis *means* (N, C, H, W, tokens, features), and write the shape as a comment beside every line.

</KeyIdea>

<Steps title="From a 224 × 224 photo to a batch">
  <Step title="Load: (H, W, C)">
    The photo arrives as a tensor of shape $(224, 224, 3)$: height, width, then the 3 colour values of each pixel.
  </Step>
  <Step title="Move the channels to the front: permute(2, 0, 1)">
    New axis 0 is old axis 2 (C = 3), then old axis 0 (H = 224), then old axis 1 (W = 224). The shape is $(3, 224, 224)$, which is (C, H, W).
  </Step>
  <Step title="Add the batch axis: unsqueeze(0)">
    A model always takes a batch, even a batch of one. A new size-1 axis at position 0 gives $(1, 3, 224, 224)$, which is (N, C, H, W). `squeeze(0)` would take it away again.
  </Step>
  <Step title="Flatten for a linear layer: flatten(1)">
    Merge every axis from 1 onwards and keep the batch axis: $3 \times 224 \times 224 = 3 \times 50176 = 150528$, so the shape is $(1, 150528)$.
  </Step>
</Steps>

```python
import torch

img = torch.rand(224, 224, 3)          # a photo as loaded: (H, W, C)
x = img.permute(2, 0, 1)               # (C, H, W)
print(x.shape)
batch = x.unsqueeze(0)                 # add the batch axis: (N, C, H, W)
print(batch.shape)
print(batch.squeeze(0).shape)          # remove it again
print(batch.flatten(1).shape)          # one long vector per image
```

```text
torch.Size([3, 224, 224])
torch.Size([1, 3, 224, 224])
torch.Size([3, 224, 224])
torch.Size([1, 150528])
```

<Mistake title="reshape is not permute">

`img.reshape(3, 224, 224)` also produces the shape $(3, 224, 224)$, and it runs without any error. But reshape pours the numbers in their stored order, so the first "channel" is really the first third of the pixels with their R, G, B values interleaved. The picture is scrambled and the model quietly learns from garbage. Moving an axis needs `permute`; regrouping needs `reshape`.

</Mistake>

### view versus reshape: contiguous memory

Under the hood, a tensor's numbers sit in one long strip of memory. The shape, together with a <Term def="For each axis, how many places to jump along the memory strip to reach the next element on that axis. A (2, 3) tensor stored row by row has strides (3, 1).">stride</Term> for each axis, says how to read that strip as a grid. `permute` and `transpose` are cheap because they move nothing: they only change the strides, so the reading order now jumps around the strip. A tensor whose reading order matches its memory order is called <Term def="Stored in memory in exactly the order you read it, row after row. x.is_contiguous() checks it. permute and transpose usually produce non-contiguous tensors.">contiguous</Term>.

`view` only relabels the strip, so it refuses when the numbers are not in reading order. `reshape` does the same as `view` when it can, and makes a contiguous copy when it must:

```python
import torch

t = torch.tensor([[1, 2, 3],
                  [4, 5, 6]])
u = t.T                        # transpose: shape (3, 2)
print(u)
print(u.is_contiguous())
print(u.reshape(6))            # reshape copies when it must
print(u.view(6))               # view refuses
```

```text
tensor([[1, 4],
        [2, 5],
        [3, 6]])
False
tensor([1, 4, 2, 5, 3, 6])
RuntimeError: view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead.
```

The fix is `u.reshape(6)` or `u.contiguous().view(6)`. You will see the second form in attention code: `out.transpose(1, 2).contiguous().view(B, T, C)`. In the lab above, apply `permute(2, 0, 1)`, switch on memory order and try `view(-1)` to watch this happen.

## Batched matrix multiplication

For two matrices, $(m \times k)$ @ $(k \times n)$ gives $(m \times n)$: the touching inner sizes must agree and disappear. With tensors of more than two dimensions, `@` follows one rule:

$$
(\underbrace{\dots}_{\text{batch}},\ m,\ k)\ @\ (\underbrace{\dots}_{\text{batch}},\ k,\ n)\ \to\ (\text{batch},\ m,\ n)
$$

Only the **last two** dims are multiplied as matrices. All the earlier dims are <Term def="Extra leading axes that just say how many separate matrix products to do at once. They are matched with the broadcasting rules: equal, 1, or missing.">batch dims</Term>: they say how many separate products to do, and they are matched with the broadcasting rules (lined up from the right, equal or 1 or missing).

The most important case is attention. The queries `Q` and keys `K` both have shape $(B, h, T, d)$: $B$ sequences in the batch, $h$ attention heads, $T$ tokens, $d$ numbers per token. Every query must be compared with every key, which is a $(T \times d)$ @ $(d \times T)$ product. `K` is stored as $(\dots, T, d)$, so its last two dims must be swapped first with `K.transpose(-2, -1)` (negative dims count from the end, so $-2, -1$ means "the last two, whatever the rank").

<BatchedMatmulShapes />

<Steps title="Shapes in attention with B = 2, h = 4, T = 5, d = 8">
  <Step title="Swap the last two dims of K">
    `K.transpose(-2, -1)` turns $(2, 4, 5, 8)$ into $(2, 4, 8, 5)$.
  </Step>
  <Step title="Match the batch dims">
    Both tensors start with $(2, 4)$, so there are $2 \times 4 = 8$ separate products, one per sequence per head.
  </Step>
  <Step title="Multiply the last two dims">
    Each product is $(5 \times 8)$ @ $(8 \times 5)$: the inner 8s agree and disappear, leaving $(5 \times 5)$, one score for every (query, key) pair.
  </Step>
  <Step title="Put it together">
    `Q @ K.transpose(-2, -1)` has shape $(2, 4, 5, 5)$, which is $(B, h, T, T)$. Softmax then turns each row into weights, and `weights @ V` is $(5 \times 5)$ @ $(5 \times 8)$ per head, giving back $(2, 4, 5, 8)$.
  </Step>
</Steps>

```python
import torch

torch.manual_seed(0)
B, h, T, d = 2, 4, 5, 8
Q = torch.randn(B, h, T, d)
K = torch.randn(B, h, T, d)
V = torch.randn(B, h, T, d)

scores = Q @ K.transpose(-2, -1)          # (B, h, T, d) @ (B, h, d, T)
print(scores.shape)
weights = torch.softmax(scores, dim=-1)   # each query's weights sum to 1
print(weights.sum(dim=-1)[0, 0])
out = weights @ V                         # (B, h, T, T) @ (B, h, T, d)
print(out.shape)
```

```text
torch.Size([2, 4, 5, 5])
tensor([1.0000, 1.0000, 1.0000, 1.0000, 1.0000])
torch.Size([2, 4, 5, 8])
```

Forgetting the transpose, `Q @ K` stops with `RuntimeError: Expected size for first two dimensions of batch2 tensor to be: [8, 8] but got: [8, 5].` The 8 in front is $B \times h = 8$ products; the error is saying "I wanted an inner size of 8 ($d$) but found 5 ($T$)".

<ExamTip>

For any `@` question, cover the batch dims with your thumb, apply the 2-D rule to the last two dims, then put the batch dims back. $(B, h, T, d)$ @ $(B, h, d, T)$ → $(B, h, T, T)$ is worth memorising, along with its partner $(B, h, T, T)$ @ $(B, h, T, d)$ → $(B, h, T, d)$. If the two inner sizes differ, the answer is an error, and `transpose(-2, -1)` is usually the fix.

</ExamTip>

## Choosing dim

Most operations take a `dim` argument (NumPy calls it `axis`) that says *along which axis* to work. Three families behave differently:

- **Reductions** (`sum`, `mean`, `max`, `argmax`): the dim you name **disappears** from the shape, unless you pass `keepdim=True`, which keeps it with size 1.
- **Softmax** keeps the shape, and makes the numbers along the named dim positive and sum to 1.
- **`torch.cat`** joins tensors along an existing dim: that dim **grows**, and every other dim must match.

The danger is that a wrong dim almost never raises an error. Try every dim for each operation and read the verdict:

<DimPicker />

The dims you will need most often:

- **Attention weights, one set per query.** Scores $(B, h, T, T)$: `torch.softmax(scores, dim=-1)` keeps the shape.
- **Join a U-Net skip connection.** `x` and `skip` are both $(N, C, H, W)$: `torch.cat([x, skip], dim=1)` gives $(N, 2C, H, W)$.
- **Average token vectors into a sentence vector.** $(B, T, d)$: `x.mean(dim=1)` gives $(B, d)$.
- **Predicted class per pixel.** Logits $(N, \text{classes}, H, W)$: `logits.argmax(dim=1)` gives $(N, H, W)$.
- **Predicted class per example.** Logits $(N, \text{classes})$: `logits.argmax(dim=1)` gives $(N,)$.

```python
import torch

logits = torch.tensor([[2.0, 0.5, -1.0],
                       [0.1, 3.0,  0.2]])   # 2 examples, 3 classes
print(logits.argmax(dim=1))       # predicted class per example
print(logits.argmax(dim=0))       # which example is best per class (not a prediction!)
print(logits.mean(dim=1, keepdim=True).shape)
x = torch.zeros(8, 64, 32, 32)
skip = torch.zeros(8, 64, 32, 32)
print(torch.cat([x, skip], dim=1).shape)
print(torch.cat([x, skip], dim=0).shape)
```

```text
tensor([0, 1])
tensor([0, 1, 1])
torch.Size([2, 1])
torch.Size([8, 128, 32, 32])
torch.Size([16, 64, 32, 32])
```

<Mistake title="The wrong dim fails silently">

`torch.softmax(scores, dim=0)` on a batch runs perfectly and returns numbers between 0 and 1. They just sum to 1 across *different sentences*, so the model trains on nonsense. Check two things: the output shape is the one you expect, and (for softmax) `out.sum(dim=-1)` is all ones.

</Mistake>

<ExamTip>

In shape questions, write the shape and cross out the dim you name for a reduction, or add the two sizes along it for `cat`. In the Final, add `assert out.shape == (B, T, d)` or a `# (B, T, d)` comment after every line of a from-scratch model: shape bugs are the number one reason a correct-looking implementation fails the hidden tests.

</ExamTip>

<Takeaways>

- A tensor is a NumPy-like array with one dtype and a shape. `torch.tensor` infers the dtype (whole numbers → int64, decimals → float32); `torch.Tensor` always gives float32. Layers, `@` and gradients need float32 on both sides: use `.float()`.
- `unsqueeze(d)` adds a size-1 axis, `squeeze` removes size-1 axes, `permute` reorders axes (each argument is an old position), `transpose` swaps two, `flatten(s)` merges, and `view`/`reshape` regroup in reading order. `view` needs contiguous memory; `reshape` copies if it must.
- Image batches are (N, C, H, W). A photo (H, W, C) becomes a batch with `.permute(2, 0, 1).unsqueeze(0)`.
- `@` multiplies the last two dims and broadcasts the rest: $(B, h, T, d)$ @ $(B, h, d, T)$ → $(B, h, T, T)$, using `K.transpose(-2, -1)`.
- Name the dim you mean: reductions remove it, softmax normalises along it (`dim=-1` in attention), `cat` grows it (`dim=1` for channels). A wrong dim rarely raises an error.

</Takeaways>
