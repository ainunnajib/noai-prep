Every PyTorch model ever trained, from a two-weight toy to a large language model, learns inside the same short loop. It is five lines long, and the **order** of those lines decides whether the model learns, learns badly, or crashes. The NOAI Final's programming tasks run in Jupyter with no internet, so you need this loop in your head, and the MCQs ask what each line does and what goes wrong when one is missing or out of place. By the end of this lesson you will know each line, why it sits where it does, and what happens when it doesn't.

<Analogy title="A practice-paper routine">

Picture a student working through practice papers with a tutor. For each paper: (1) wipe the whiteboard of the last paper's corrections, (2) attempt the questions, (3) mark them to get a score, (4) trace each wrong answer back to the habit that caused it, (5) adjust those habits a little. Then the next paper. Skip the wipe and today's corrections pile on top of yesterday's. Adjust your habits before tracing the mistakes and you fix the wrong things.

</Analogy>

## Three objects you create once

Before the loop starts, you build three things:

```python
import torch
import torch.nn as nn

model = nn.Linear(1, 1, bias=False)                        # the model: y_hat = w * x
criterion = nn.MSELoss()                                   # the loss function
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)    # the optimiser
```

- The **model** turns inputs into predictions. Here it has a single weight $w$.
- The **criterion** is the <Term def="A function that scores how wrong the predictions are, as one number. Training tries to make it small. Examples: mean squared error for numbers, cross-entropy for classes.">loss function</Term>: it compares predictions with the true answers and returns one number, the loss.
- The **optimiser** holds a list of the model's weights (that is what `model.parameters()` hands it) and knows how to nudge them. `SGD` is plain gradient descent; `lr` is the <Term def="The size of each step the optimiser takes against the gradient. Too small: slow learning. Too big: the loss jumps around or blows up.">learning rate</Term>. PyTorch's code uses the American spelling `optimizer`, so we do too inside code.

## The five lines of every training step

```python
for inputs, targets in train_loader:     # one batch at a time
    optimizer.zero_grad()                # 1. clear the old gradients
    outputs = model(inputs)              # 2. forward pass: make predictions
    loss = criterion(outputs, targets)   # 3. measure how wrong they are
    loss.backward()                      # 4. backward pass: compute gradients
    optimizer.step()                     # 5. update the weights
```

1. **`optimizer.zero_grad()`** empties every weight's `.grad` (since PyTorch 2.0 it sets them to `None`). This matters because PyTorch never overwrites a gradient: it *adds* to it.
2. **`outputs = model(inputs)`** runs the forward pass. Autograd records every operation so it can work backwards later.
3. **`loss = criterion(outputs, targets)`** turns the predictions into one number.
4. **`loss.backward()`** runs backpropagation through the recorded graph and **adds** $\partial L/\partial w$ into `w.grad` for every weight $w$.
5. **`optimizer.step()`** reads each `.grad` and moves each weight. A weight whose `.grad` is `None` is skipped.

Now break it. The figure below lets you reorder and delete these lines; each version was really run in PyTorch, so what you see is what PyTorch does.

<TrainingLoopOrder />

<KeyIdea>

**zero_grad → forward → loss → backward → step.** Clear, predict, measure, blame, adjust. The only freedom is *where* `zero_grad()` goes: anywhere after the previous `step()` and before this `backward()` (many people put it last in the loop). It must never sit between `backward()` and `step()`.

</KeyIdea>

For plain SGD, line 5 performs, for every weight $w$,

$$
w \leftarrow w - \eta \, \frac{\partial L}{\partial w}
$$

Here $w$ is one weight, $L$ is the loss of this batch, $\frac{\partial L}{\partial w}$ is the gradient that `backward()` stored in `w.grad` (how much the loss rises if $w$ rises a little), $\eta$ ("eta") is the learning rate, and the arrow means "replace $w$ by". In words: take a small step downhill. Other optimisers, such as Adam, use the same `.grad` in a cleverer formula; the five lines do not change.

## One training step by hand

Let's run the loop by hand on a model with one weight, $\hat y = w x$, two training examples $(x, y) = (1, 2)$ and $(2, 4)$, mean squared error, starting weight $w = 0$ and learning rate $\eta = 0.1$. (The perfect weight is $w = 2$.)

<Steps title="First pass through the five lines">
  <Step title="zero_grad">
    `w.grad` becomes `None`: nothing stored yet.
  </Step>
  <Step title="Forward pass">
    With $w = 0$ both predictions are $\hat y = 0 \times 1 = 0$ and $0 \times 2 = 0$.
  </Step>
  <Step title="Loss">
    Mean squared error averages the squared errors: $L = \frac{(0-2)^2 + (0-4)^2}{2} = \frac{4 + 16}{2} = 10$.
  </Step>
  <Step title="Backward: $\partial L/\partial w$">
    Each squared error $(w x_i - y_i)^2$ has derivative $2(w x_i - y_i)\,x_i$. Averaging: $\frac{2(-2)(1) + 2(-4)(2)}{2} = \frac{-4 - 16}{2} = -10$. So `w.grad` $= -10$. Negative means "increasing $w$ lowers the loss".
  </Step>
  <Step title="Step">
    $w \leftarrow 0 - 0.1 \times (-10) = 1$. The weight moved halfway towards 2.
  </Step>
</Steps>

Repeat at $w = 1$: errors $-1$ and $-2$, loss $\frac{1 + 4}{2} = 2.5$, gradient $\frac{2(-1)(1) + 2(-2)(2)}{2} = -5$, new $w = 1 + 0.5 = 1.5$. Each pass halves the distance to 2.

Now **forget `zero_grad()`**. The second `backward()` adds $-5$ onto the $-10$ already stored, so `w.grad` $= -15$ and the step jumps to $w = 1 + 1.5 = 2.5$, past the answer. Here are both versions run in PyTorch:

```python
x = torch.tensor([[1.0], [2.0]])
y = torch.tensor([[2.0], [4.0]])
# (model, criterion, optimizer as above, with the weight set to 0)

for step in range(3):
    optimizer.zero_grad()              # delete this line for the second run
    outputs = model(x)
    loss = criterion(outputs, y)
    loss.backward()
    print(f"step {step+1}: loss {loss.item():.3f}, grad {model.weight.grad.item():.2f}", end="")
    optimizer.step()
    print(f", new w {model.weight.item():.2f}")
```

```text
step 1: loss 10.000, grad -10.00, new w 1.00
step 2: loss 2.500, grad -5.00, new w 1.50
step 3: loss 0.625, grad -2.50, new w 1.75
```

```text
step 1: loss 10.000, grad -10.00, new w 1.00
step 2: loss 2.500, grad -15.00, new w 2.50
step 3: loss 0.625, grad -12.50, new w 3.75
```

Without `zero_grad()` the weight overshoots to 2.5 and then runs away to 3.75, because every step still carries the old gradients. (`loss.item()` turns a one-number tensor into a plain Python number, the right way to print or log a loss.)

<Mistake title="Two silent killers">

- **Missing `zero_grad()`**: no error, but gradients from every earlier batch pile up, so training is erratic or diverges.
- **`zero_grad()` between `backward()` and `step()`**, or `step()` before `backward()` right after `zero_grad()`: no error, but `step()` always finds `.grad` empty, so the weights never move. The loss stays flat.

Neither raises an error, which is why exam questions love them. When the loss will not budge, read the order of these five lines first.

</Mistake>

## Datasets and DataLoaders: where batches come from

Models are trained on a <Term def="A small group of training examples processed together in one forward and backward pass. The batch size is how many examples it holds.">batch</Term> of examples at a time, not the whole dataset at once: it is faster on a GPU and fits in memory. PyTorch splits the job in two:

- A **`Dataset`** knows how many examples there are (`__len__`) and how to fetch example number `i` (`__getitem__`), for instance by reading one image file and its label.
- A **`DataLoader`** wraps a Dataset and hands out batches: it stacks examples into one tensor, can **shuffle** the order every epoch, and can load in parallel with `num_workers`.

<Analogy title="The canteen tray line">

The kitchen (the Dataset) cooks one plate at a time. The tray line (the DataLoader) puts plates on trays of a fixed size and sends trays out to the tables, in a fresh mixed order each lunchtime so no table gets only one stall's dishes.

</Analogy>

One full pass through the training set is an <Term def="One complete pass through every example in the training set. Training usually runs for many epochs.">epoch</Term>; one batch, with its five-line update, is an <Term def="One batch through the five-line training step: one forward pass, one backward pass and one weight update. Also called a step.">iteration</Term>.

```python
from torch.utils.data import TensorDataset, DataLoader

torch.manual_seed(0)
X = torch.randn(12, 1, 28, 28)   # 12 greyscale 28x28 images
y = torch.arange(12)             # label = its index, so we can see the order

ds = TensorDataset(X, y)
print(len(ds), ds[3][0].shape, ds[3][1])

loader = DataLoader(ds, batch_size=5, shuffle=True)
print("batches per epoch:", len(loader))
for epoch in range(2):
    for xb, yb in loader:
        print(epoch, tuple(xb.shape), yb.tolist())
```

```text
12 torch.Size([1, 28, 28]) tensor(3)
batches per epoch: 3
0 (5, 1, 28, 28) [5, 11, 0, 6, 1]
0 (5, 1, 28, 28) [9, 2, 7, 8, 10]
0 (2, 1, 28, 28) [3, 4]
1 (5, 1, 28, 28) [1, 7, 5, 0, 10]
1 (5, 1, 28, 28) [6, 2, 4, 11, 9]
1 (2, 1, 28, 28) [8, 3]
```

Each example has shape `(1, 28, 28)`; the DataLoader stacks 5 of them into a batch of shape `(5, 1, 28, 28)`, the $(N, C, H, W)$ layout from the tensors lesson. Twelve does not divide by 5, so the last batch has only 2 examples. Every example is used exactly once per epoch, in a new order each time.

<DataLoaderShuffle />

Why shuffle the training data? Files are often stored in order (all cats, then all dogs; or by date). Without shuffling, the model sees long runs of one kind of example, and each run of updates drags the weights towards that kind before the next run drags them back. Shuffling makes every batch a fair sample of the data. Validation and test data need **no** shuffling: you only measure them.

<KeyIdea>

With $N$ examples and batch size $B$, one epoch has $\lceil N/B \rceil$ iterations, where $\lceil \cdot \rceil$ means "round up" because the last, smaller batch still counts. With `drop_last=True` that smaller batch is thrown away, giving $\lfloor N/B \rfloor$ ("round down").

</KeyIdea>

<ExamTip>

Iteration counting is quick no-calculator arithmetic. $N = 1000$, $B = 32$: $32 \times 31 = 992$, leaving 8, so there are 32 iterations per epoch (31 with `drop_last=True`). Ten epochs means 320 weight updates. Watch the words: "one epoch" is a whole pass over the data, never "one batch" or "one update".

</ExamTip>

## The whole loop: epochs, training and validation

A real script wraps the five lines in a loop over epochs and checks the model on held-out <Term def="Data kept aside from training and used only to measure how well the model does on examples it has not learned from.">validation</Term> data after each one:

```python
torch.manual_seed(0)
# toy data: 2 features; label 1 if the point lies inside the unit circle
X = torch.randn(600, 2)
y = (X.pow(2).sum(dim=1) < 1).long()
train_ds = TensorDataset(X[:500], y[:500])
val_ds = TensorDataset(X[500:], y[500:])
train_loader = DataLoader(train_ds, batch_size=32, shuffle=True)
val_loader = DataLoader(val_ds, batch_size=100)

model = nn.Sequential(nn.Linear(2, 16), nn.ReLU(), nn.Dropout(0.2), nn.Linear(16, 2))
criterion = nn.CrossEntropyLoss()
optimizer = torch.optim.Adam(model.parameters(), lr=0.01)

for epoch in range(5):
    model.train()                        # dropout ON
    total = 0.0
    for inputs, targets in train_loader:
        optimizer.zero_grad()
        outputs = model(inputs)
        loss = criterion(outputs, targets)
        loss.backward()
        optimizer.step()
        total += loss.item() * len(inputs)

    model.eval()                         # dropout OFF
    correct = 0
    with torch.no_grad():                # no graph needed
        for inputs, targets in val_loader:
            preds = model(inputs).argmax(dim=1)
            correct += (preds == targets).sum().item()
    print(f"epoch {epoch+1}: train loss {total/len(train_ds):.3f}, "
          f"val accuracy {correct/len(val_ds):.2f}")
```

```text
epoch 1: train loss 0.650, val accuracy 0.56
epoch 2: train loss 0.536, val accuracy 0.61
epoch 3: train loss 0.457, val accuracy 0.80
epoch 4: train loss 0.408, val accuracy 0.88
epoch 5: train loss 0.363, val accuracy 0.92
```

Three details are worth copying exactly. `total += loss.item() * len(inputs)` uses `.item()`, so it adds plain numbers instead of keeping every batch's graph alive in memory. The validation part never calls `backward()` or `step()`: it only measures. And it is wrapped in `model.eval()` and `torch.no_grad()`, which do two *different* jobs.

## Train mode and eval mode

Some layers behave differently while training. Two you will meet everywhere:

- <Term def="A layer that, during training, sets each value to zero with probability p and multiplies the survivors by 1/(1−p). It stops the network relying on any single unit, which reduces overfitting.">Dropout</Term> randomly zeroes units during training.
- <Term def="Batch normalisation: a layer that rescales each feature using the mean and variance of the current batch while training, and keeps running averages of them to use at test time.">BatchNorm</Term> normalises each feature with the current batch's mean and variance, and keeps running averages of them for later.

`model.train()` and `model.eval()` flip a switch (`model.training`) that these layers read. They do not train or evaluate anything by themselves.

<TrainEvalToggle />

| Switch | Dropout | BatchNorm | Graph recorded? |
|---|---|---|---|
| `model.train()` | drops units at random, scales the rest by $\frac{1}{1-p}$ | batch statistics; updates running averages | yes |
| `model.eval()` | off | stored running averages | yes |
| `torch.no_grad()` | unchanged | unchanged | **no** |

The same input gives a different output every time in train mode, which is exactly what you want while training and exactly what you do not want while measuring:

```python
torch.manual_seed(0)
drop = nn.Dropout(p=0.5)
x = torch.ones(8)

drop.train()
print(drop(x))
print(drop(x))

drop.eval()
print(drop(x))
print(drop.training)
```

```text
tensor([0., 0., 2., 0., 0., 0., 2., 2.])
tensor([0., 2., 2., 2., 2., 0., 2., 2.])
tensor([1., 1., 1., 1., 1., 1., 1., 1.])
False
```

In train mode about half the ones become 0 and the survivors become $1 \times \frac{1}{1 - 0.5} = 2$, so the *average* stays about the same. In eval mode the input passes through untouched.

<Mistake title="eval() and no_grad() are not the same switch">

- Forgetting `model.eval()` before validation: no error, but dropout is still dropping and BatchNorm uses each validation batch's own statistics, so your validation scores are noisy and wrong.
- Using `torch.no_grad()` *instead of* `model.eval()`: it saves memory, but dropout and BatchNorm still behave as in training.
- Forgetting `model.train()` at the start of the next epoch: dropout stays off and BatchNorm stops updating, so training quietly changes. That is why the loop above calls `model.train()` at the top of every epoch.

</Mistake>

## Gradient accumulation: a big batch in a small GPU

Sometimes a batch of 32 does not fit in GPU memory but a batch of 8 does. You can still get the same update as batch 32 by running **4 micro-batches of 8** and letting their gradients add up before one `step()`. This trick, **gradient accumulation**, uses the very behaviour that made `zero_grad()` necessary.

```python
accumulation_steps = 4
optimizer.zero_grad()
for i, (inputs, targets) in enumerate(train_loader):    # batches of 8
    loss = criterion(model(inputs), targets)
    loss = loss / accumulation_steps                     # Line A
    loss.backward()                                      # .grad += ...
    if (i + 1) % accumulation_steps == 0:                # every 4th batch
        optimizer.step()
        optimizer.zero_grad()
```

Why Line A? Each micro-batch loss $L_k$ is already a **mean** over its 8 examples. If the 4 micro-batches are the same size, the mean over all 32 examples is the average of the 4 means, so its gradient is

$$
\nabla \Big( \frac{1}{4} \sum_{k=1}^{4} L_k \Big) = \frac{1}{4} \sum_{k=1}^{4} \nabla L_k
$$

where $\nabla L_k$ is the gradient of micro-batch $k$'s loss. Four `backward()` calls only produce the sum $\sum_k \nabla L_k$, which is **4 times** too big. Dividing each loss by 4 first supplies the missing $\frac{1}{4}$.

<GradAccumulation />

Run in PyTorch, accumulated gradients with Line A match one real batch of 32 exactly:

```python
torch.manual_seed(0)
X, y = torch.randn(32, 3), torch.randn(32, 1)
model = nn.Linear(3, 1)
criterion = nn.MSELoss()

model.zero_grad()                                   # (a) one batch of 32
criterion(model(X), y).backward()
big = model.weight.grad.clone()

model.zero_grad()                                   # (b) 4 micro-batches of 8
for i in range(4):
    xb, yb = X[i*8:(i+1)*8], y[i*8:(i+1)*8]
    loss = criterion(model(xb), yb) / 4
    loss.backward()
acc = model.weight.grad.clone()

print(big)
print(acc)
print(torch.allclose(big, acc))
```

```text
tensor([[ 0.1699, -0.6698, -0.8743]])
tensor([[ 0.1699, -0.6698, -0.8743]])
True
```

<ExamTip>

Accumulation questions test three facts. The **effective batch size** is micro-batch × steps ($8 \times 4 = 32$). Memory is that of one micro-batch (8), because only one micro-batch's activations exist at a time. And it is **not faster**: the micro-batches run one after another. (One small catch: BatchNorm still computes its statistics on micro-batches of 8.)

</ExamTip>

<Takeaways>

- Every training step is **zero_grad → forward → loss → backward → step**; `zero_grad()` may also go last, but never between `backward()` and `step()`.
- `backward()` **adds** into `.grad`. Forget `zero_grad()` and old gradients pile up; clear them before `step()` and nothing is learned. Neither raises an error.
- A `Dataset` gives single examples; a `DataLoader` batches and (for training) shuffles them every epoch. One epoch is $\lceil N/B \rceil$ iterations.
- Validate with **both** `model.eval()` (dropout off, BatchNorm uses running averages) and `torch.no_grad()` (no graph), then switch back with `model.train()`.
- Gradient accumulation: divide each loss by the number of micro-batches, call `step()` once every $k$ batches; effective batch = micro-batch × $k$.

</Takeaways>
