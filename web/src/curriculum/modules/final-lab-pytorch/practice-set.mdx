## Work test-first

Hidden tests are why "it ran without errors" is not the same as "it is correct". The habit that protects you is **test-first** work: before you write the function, work out a tiny example by hand and write it as a test. Then the moment your code runs, you know whether it is right.

<Steps title="Test-first, on precision, recall and F1">
  <Step title="Read the signature and the rules">
    `precision_recall_f1(y_true, y_pred)` returns three Python floats, and a score whose denominator is 0 must be 0.0. Note both rules: each is a likely hidden test.
  </Step>
  <Step title="Make a tiny example and solve it by hand">
    `y_true = [1, 0, 1, 1, 0]`, `y_pred = [1, 1, 0, 1, 0]`. A <Term def="A positive prediction that is correct: predicted 1, truly 1.">true positive</Term> (TP) is predicted 1 and truly 1: positions 0 and 3, so TP = 2. A false positive (FP) is predicted 1 but truly 0: position 1, so FP = 1. A false negative (FN) is predicted 0 but truly 1: position 2, so FN = 1.
  </Step>
  <Step title="Turn it into expected numbers">
    Precision $= \frac{TP}{TP + FP} = \frac{2}{3}$, recall $= \frac{TP}{TP + FN} = \frac{2}{3}$, and $F_1 = \frac{2PR}{P + R} = \frac{2 \cdot \frac{4}{9}}{\frac{4}{3}} = \frac{2}{3}$.
  </Step>
  <Step title="Write the assert, then the code">
    `assert np.allclose(precision_recall_f1([1, 0, 1, 1, 0], [1, 1, 0, 1, 0]), (2/3, 2/3, 2/3))`. Now implement until it passes.
  </Step>
  <Step title="Think like the hidden tests">
    What could break? No predicted positives makes precision $0/0$; huge inputs, ties, empty arrays and the wrong return type are the other usual suspects. Add one assert for each that applies.
  </Step>
</Steps>

<Mistake title="The edge cases hidden tests love">

Every task above has at least one hidden test that a correct-looking first draft fails:

- **Division by zero:** no predicted positives (precision), two empty masks (Dice), a constant row (normalisation). Guard the denominator, or add a small `eps` as the formula says.
- **Overflow:** `np.exp(1000)` is `inf`. Subtract each row's maximum before a softmax.
- **Ties:** a tied vote or two equal distances. Read the docstring for the tie rule; `np.bincount(votes).argmax()` picks the smallest label. (In the browser runner, which is 32-bit, `np.bincount` only accepts the platform integer type, so convert first: `votes.astype(np.intp)`.)
- **Conventions:** biased versus unbiased variance, a flipped kernel, a regularised bias. When the docstring names a convention, a hidden test checks it.
- **Return types and shapes:** a NumPy scalar where a Python `float` was asked for, or `(n,)` where `(n, 1)` was asked for.

</Mistake>

The Final may ask for the same idea in PyTorch, so check the translation too. Here is layer normalisation compared with PyTorch's own `nn.LayerNorm`. Note `unbiased=False`: `torch.var` divides by $D - 1$ by default, but normalisation layers divide by $D$.

```python
import torch
import torch.nn as nn

def layer_norm(x, gamma, beta, eps=1e-5):
    mean = x.mean(dim=-1, keepdim=True)
    var = x.var(dim=-1, keepdim=True, unbiased=False)   # biased variance
    return gamma * (x - mean) / torch.sqrt(var + eps) + beta

torch.manual_seed(0)
x = torch.randn(4, 6)
ln = nn.LayerNorm(6)                         # gamma = 1s, beta = 0s
print(torch.allclose(layer_norm(x, ln.weight, ln.bias), ln(x), atol=1e-6))
# torch.var divides by D - 1 unless you say otherwise:
wrong = (x - x.mean(-1, keepdim=True)) / torch.sqrt(x.var(-1, keepdim=True) + 1e-5)
print(torch.allclose(wrong, ln(x), atol=1e-6))
```

```text
True
False
```

## From loops to vectors

Your first draft of a convolution will probably have four nested loops: two over output positions, two over the kernel. That is fine for correctness. But Python runs each step of a loop one at a time, and an image of $256 \times 256$ with a $3 \times 3$ kernel needs over half a million multiply-adds. <Term def="Rewriting code so that one array operation (run inside NumPy's compiled code) replaces a Python loop over the elements.">Vectorising</Term> means restructuring the same arithmetic so that NumPy (or PyTorch) runs the loops inside fast compiled code.

For convolution the classic trick is called <Term def="'Image to columns': copy every window that the kernel visits into one row (or column) of a matrix, so the whole convolution becomes one matrix multiplication.">im2col</Term>: copy every $k \times k$ window of the image into one row of a **patch matrix**, flatten the kernel into a vector, and do **one** matrix-vector product. Row $r$ of the result is exactly the output at window $r$. Step through both versions:

<Conv2dLoopVisual />

<Steps title="im2col for a 3 × 3 image and a 2 × 2 kernel">
  <Step title="Count the windows">
    The output side is $3 - 2 + 1 = 2$, so there are $2 \times 2 = 4$ windows, each with $2 \times 2 = 4$ numbers. The patch matrix is $4 \times 4$.
  </Step>
  <Step title="Fill the rows">
    Image $\begin{bmatrix} 1 & 2 & 3 \\ 4 & 5 & 6 \\ 7 & 8 & 9 \end{bmatrix}$. The top-left window, read row by row, is $[1, 2, 4, 5]$; then $[2, 3, 5, 6]$, $[4, 5, 7, 8]$ and $[5, 6, 8, 9]$.
  </Step>
  <Step title="One product">
    The kernel $\begin{bmatrix} 1 & 0 \\ 0 & 1 \end{bmatrix}$ flattens to $[1, 0, 0, 1]$. Each row's dot product adds its first and last entries: $[6, 8, 12, 14]$, which reshapes to $\begin{bmatrix} 6 & 8 \\ 12 & 14 \end{bmatrix}$.
  </Step>
</Steps>

PyTorch has im2col built in as `F.unfold`, and you can check that it matches `F.conv2d` exactly:

```python
import torch
import torch.nn.functional as F

x = torch.arange(1., 10.).view(1, 1, 3, 3)      # (N, C, H, W), values 1 to 9
w = torch.tensor([[1., 0.], [0., 1.]]).view(1, 1, 2, 2)
cols = F.unfold(x, kernel_size=2)               # (N, C*k*k, windows) = (1, 4, 4)
print(cols[0].T)                                # one window per row
print((cols[0].T @ w.view(-1)).view(2, 2))
print(F.conv2d(x, w)[0, 0])
```

```text
tensor([[1., 2., 4., 5.],
        [2., 3., 5., 6.],
        [4., 5., 7., 8.],
        [5., 6., 8., 9.]])
tensor([[ 6.,  8.],
        [12., 14.]])
tensor([[ 6.,  8.],
        [12., 14.]])
```

In NumPy, `numpy.lib.stride_tricks.sliding_window_view(image, (k, k))` builds all the windows without copying, and one `reshape` turns them into the patch matrix. The timing code in the visual compares the two versions; one run of it on our test machine printed:

```text
64 x 64 image, 3 x 3 kernel in your browser:
loops     41.26 ms
im2col    0.125 ms   (331 times faster)
largest difference between the outputs: 3.6e-15
```

The exact times vary from run to run and machine to machine; a speed-up of tens to hundreds of times does not. The difference of $3.6 \times 10^{-15}$ is rounding: the two versions add the same numbers in a different order.

<ExamTip title="When to vectorise in the exam">

Vectorise only after the loop version passes its tests, and only if time allows or the task demands speed (a large test input, or "do not use Python loops over pixels" in the instructions). Keep the loop version in a scratch cell and compare with `np.allclose`. The 2026 mean-IoU task is a good model: loop over the few classes, but never over the many pixels.

</ExamTip>

<Takeaways>

- Past Finals set classical ML from scratch in NumPy every year, and since 2026 PyTorch components with a debugging part; all are graded by tests, many of them hidden.
- Likely candidates include logistic regression with L2, k-NN, stable softmax cross-entropy, PCA, a Gini split, precision/recall/F1, conv2d, BatchNorm or LayerNorm, Dice loss and a CNN shape fix. Practise the patterns, not just the past tasks.

- Vectorising restructures the same arithmetic so the library runs the loops: im2col turns a convolution into one matrix product, tens to hundreds of times faster, with the same answer.

</Takeaways>
