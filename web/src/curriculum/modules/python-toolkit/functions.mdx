## Defining and calling a function

<Analogy title="A drink vending machine">

You put in coins and press a choice (the inputs), the machine does its work inside, and a can drops out of the chute (the output). You don't need to know how it works inside to use it, and you can use it again and again.

</Analogy>

A <Term def="A named, reusable block of code. You define it once with def, then run it as many times as you like by calling it.">function</Term> packages a calculation under a name:

```python
def area(w, h):          # def, the name, the parameters, a colon
    return w * h         # the indented body; return hands back a value

a = area(3, 4)           # call the function with arguments 3 and 4
print(a)                 # 12
print(area(5, 2) + 1)    # 11: the returned value can be used in a sum
```

Reading it piece by piece:

- `def` starts a function definition, and `area` is its name.
- `w` and `h` are <Term def="The names listed in brackets in a def line. They receive the values passed in when the function is called.">parameters</Term>: empty slots waiting for values.
- The indented lines are the **body**. They run only when the function is **called**, never when it is defined.
- `area(3, 4)` is a <Term def="Running a function by writing its name followed by brackets containing the arguments, e.g. area(3, 4).">call</Term>. The values `3` and `4` are <Term def="The actual values you pass into a function when you call it. They are matched to the parameters.">arguments</Term>, and they are matched to the parameters in order: `w = 3`, `h = 4`.
- `return w * h` sends the result back to wherever the call was made, so `area(3, 4)` turns into `12`.

## return versus print

This is the most common beginner mix-up, and examiners know it. `print` **shows** a value on the screen; `return` **hands it back** to the code that called the function. A function that never reaches a `return` hands back the special value `None`, meaning "nothing".

```python
def double(x):
    print(x * 2)     # shows 8, but returns nothing

y = double(4)
print(y)
```

```text
8
None
```

The `8` appears while `double` runs, but `y` receives `None`, so `y + 1` would crash with `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`. Two more facts about `return`:

- It ends the function immediately. Any lines after it in the body do not run.
- It can hand back several values at once as a tuple: `return min(nums), max(nums)`. Then `lo, hi = min_max([4, 1, 7])` unpacks them, giving `lo = 1` and `hi = 7`.

<KeyIdea>

Parameters are the slots; arguments are the values you pass in. **return** hands a value back so later code can use it. **print** only displays it, and a function without return gives back **None**.

</KeyIdea>

## Default values and keyword arguments

A parameter can have a <Term def="A value written in the def line, as in lr=0.1. It is used whenever the caller leaves that argument out.">default value</Term>, which is used when the caller leaves that argument out. This is how ML libraries let you call a model with sensible settings and change only the ones you care about.

```python
def update(w, grad, lr=0.1):
    return w - lr * grad

print(update(2.0, 4))          # lr not given, so the default 0.1 is used
print(update(2.0, 4, lr=0.5))  # a keyword argument sets lr by name
```

```text
1.6
0.0
```

Arguments matched by their position, like `2.0` and `4`, are <Term def="An argument matched to a parameter by its position in the call: the first argument fills the first parameter, and so on.">positional arguments</Term>. Writing `lr=0.5` in the call is a <Term def="An argument passed as name=value, e.g. lr=0.5. It goes to the parameter with that name, so the order does not matter.">keyword argument</Term>: it goes to the parameter called `lr`, wherever that parameter is in the list. Two rules keep Python from getting confused:

- In the `def` line, parameters with defaults come **after** those without: `def f(x=1, y):` is a `SyntaxError`.
- In a call, keyword arguments come **after** positional ones: `update(lr=0.5, 2.0, 4)` is a `SyntaxError`.

<Steps title="Trace update(2.0, 4) by hand">
  <Step title="Match the arguments">
    Positional arguments fill parameters in order: `w = 2.0` and `grad = 4`. Nothing was passed for `lr`, so it takes its default, `lr = 0.1`.
  </Step>
  <Step title="Work out the body">
    $\text{lr} \times \text{grad} = 0.1 \times 4 = 0.4$, and $w - 0.4 = 2.0 - 0.4 = 1.6$.
  </Step>
  <Step title="Return">
    `return` hands back `1.6`, and `print` shows it.
  </Step>
  <Step title="Now with lr=0.5">
    $0.5 \times 4 = 2.0$, and $2.0 - 2.0 = 0.0$. This tiny function is exactly one step of <Term def="The method that trains most AI models: repeatedly nudge each weight a small step in the direction that lowers the loss.">gradient descent</Term>: $w_{\text{new}} = w - \eta \cdot \text{gradient}$, where $\eta$ (eta) is the <Term def="A small positive number that sets how big each training step is. You choose it before training.">learning rate</Term> `lr`.
  </Step>
</Steps>

## Scope: where Python looks for a name

<Analogy title="A classroom and the school PA system">

An announcement made in your classroom stays in your classroom. An announcement over the PA system reaches every class. Variables created inside a function are like classroom announcements: the rest of the program never hears them.

</Analogy>

A variable created inside a function (including its parameters) is a <Term def="A variable created inside a function, including its parameters. It exists only while that call is running.">local variable</Term>. It exists only while that call runs, and it disappears when the function returns. A variable created in the main program, outside every function, is a <Term def="A variable created in the main program, outside every function. Every part of the program can read it.">global variable</Term>. The part of a program where a name can be seen is its <Term def="The region of a program in which a name can be used. Each function call has its own local scope.">scope</Term>.

When Python meets a name, it searches the scopes from the inside out, in an order called the **LEGB rule**:

1. **Local**: the function that is running right now.
2. **Enclosing**: the function this one is defined inside, if there is one.
3. **Global**: the main program.
4. **Built-in**: Python's own names, such as `print` and `len`.

It uses the first match it finds. If there is none, you get a `NameError`. The Enclosing step only matters when one function is defined inside another:

```python
x = 'global'

def outer():
    x = 'enclosing'
    def inner():
        return x      # no local x, so look outwards
    return inner()

print(outer())
```

```text
enclosing
```

`inner` has no `x` of its own, so Python checks the enclosing function `outer` next and finds `'enclosing'` there. It never reaches the global `x`.

<ScopeBubbles />

<KeyIdea>

Lookup goes from the inside out: local, enclosing, global, built-in (**LEGB**), so a function can read a global. But assigning to a name inside a function creates a brand-new **local** variable with that name: not a copy of the global (it has no value until you assign one), and the global is left alone.

</KeyIdea>

<Mistake title="UnboundLocalError: updating a global inside a function">

```python
count = 0
def add_one():
    count = count + 1   # crashes
add_one()
```

Because `count` is assigned somewhere inside `add_one`, Python treats `count` as local **everywhere** in that function. So the right-hand side tries to read a local `count` that has no value yet: `UnboundLocalError: cannot access local variable 'count' where it is not associated with a value`. The clean fix is to pass the value in and return the new one: `def add_one(count): return count + 1`, then `count = add_one(count)`. (Python also has a `global count` statement, and `nonlocal count`, which does the same job for a variable of an enclosing function. Use them sparingly: code that changes outside variables from inside a function is hard to debug.)

</Mistake>

## *args and **kwargs: any number of arguments

<Analogy title="The 'extras' bag at check-in">

At an airport counter, your suitcase gets its own tag. Loose extras go into one bag, in the order you hand them over. Extras that carry name tags go into a separate pouch, where each one is found by its tag. Python does the same when a function is called with more arguments than it has named parameters: the bag is `*args` and the pouch is `**kwargs`.

</Analogy>

Sometimes a function should accept *any* number of arguments, like `print`, which happily takes one, two or ten. A parameter written with one star, `*args`, collects all the extra **positional** arguments into a **tuple**. A parameter with two stars, `**kwargs`, collects all the extra **keyword** arguments into a **dict**.

```python
def total(*args):
    return sum(args)

print(total(1, 2, 3))   # 6: args is the tuple (1, 2, 3)
print(total())          # 0: args is the empty tuple ()

def describe(**kwargs):
    for key, value in kwargs.items():
        print(key, '=', value)

describe(lr=0.1, epochs=5)   # kwargs is {'lr': 0.1, 'epochs': 5}
```

```text
6
0
lr = 0.1
epochs = 5
```

<ArgsPacker />

Python fills the parameters in a fixed order: normal parameters first (by position, or by name for keyword arguments), then `*args` takes the leftover positional arguments, then `**kwargs` takes the leftover keyword arguments. The names `args` and `kwargs` are only a convention; the stars do the work.

<Note title="Stars in a call">

The stars also work the other way round when you *call* a function. `*` spreads a list or tuple into positional arguments, and `**` spreads a dict into keyword arguments:

```python
def f(a, b):
    print(a, b)

f(*[1, 2])              # same as f(1, 2)
f(**{'a': 1, 'b': 2})   # same as f(a=1, b=2)
```

```text
1 2
1 2
```

You will see `model(**inputs)` in <Term def="A popular library of ready-made, pretrained AI models such as BERT and GPT-2.">Hugging Face</Term> code for exactly this reason: `inputs` is a dict of named tensors.

</Note>

<PastPaperQuestion paper="prelim2026" n={85} />

<ExamTip>

One star means a tuple of extra **positional** arguments; two stars mean a dict of extra **keyword** arguments. Expect distractors that swap the two, or that describe default values (`def f(x=0)`) instead. In "what does this print?" questions, remember that a one-item tuple prints with a comma, `(3,)`, and that a function without `return` gives `None`.

</ExamTip>

<Note title="Type hints: labels, not rules">

Exam scaffolds often write a function like this:

```python
def area(w: float, h: float) -> float:
    return w * h
```

`: float` after a parameter says what type should go in, and `-> float` before the final colon says what comes out. These **type hints** are labels for readers and tools. Python does not enforce them, so `area(3, 4)` still returns `12`. They are different from default values (`w=0`) and from `*args`. The 2026 Final's gradient functions were written this way, with `np.ndarray` (a NumPy array) as the type.

</Note>

<Note title="One-line functions: lambda">

`lambda x: x ** 2` is a tiny function with no name. It is handy when another function needs a function as its input, for example `sorted(['kopi', 'teh', 'bandung'], key=lambda w: len(w))` sorts by length and gives `['teh', 'kopi', 'bandung']`.

</Note>

<Takeaways>

- `def name(params):` defines a function; its body runs only when you call `name(args)`, and arguments are matched to parameters in order or by name.
- `return` hands a value back to the caller; `print` only displays it. With no `return`, a function gives `None`.
- Defaults such as `lr=0.1` make arguments optional, and keyword arguments set them by name.
- Variables made inside a function are local. Lookup goes local, enclosing, global, built-in (LEGB).
- `*args` packs extra positional arguments into a tuple; `**kwargs` packs extra keyword arguments into a dict.

</Takeaways>
