You change list `b`, and list `a` changes too. It feels like a bug, but Python is doing exactly what it was designed to do. Once you picture **names as arrows pointing at objects**, this whole family of surprises becomes predictable, and so do the NOAI questions built on them.

## Names are labels, not boxes

You may have pictured a variable as a box with a value inside. For Python, that picture breaks down. A better picture is a **name tag tied to a thing**: the value lives somewhere in memory, and the name is just attached to it.

<Analogy title="A shared Google Doc">
When your CCA teacher shares a Google Doc link with two students, nobody gets their own copy. Both links lead to **one** document, so if Wei Ling edits it, Arjun sees the edit. Python names work like those links: `b = a` hands out a second link to the same thing. It does not photocopy the document.
</Analogy>

Three words make this precise:

- An <Term def="Any value Python keeps in memory: a number, a string, a list, a dict, even a function. Every object has a type, a value and an identity (its id).">object</Term> is a value living in memory, such as the list `[1, 2]`.
- A <Term def="A variable name such as a or scores. It holds no data itself; it refers to an object.">name</Term> (a variable) is a label you use to reach an object.
- A <Term def="The link from a name to an object, drawn as an arrow. Following it takes you to the object itself, never to a copy.">reference</Term> is the arrow from a name to its object.

So `a = [1, 2]` does **two** things: it builds a list object, then it points the name `a` at it.

<KeyIdea>
`name = something` works out the object on the right, then points the name on the left at it. **Assignment moves arrows. It never copies objects.**
</KeyIdea>

### Mutate or rebind?

Everything you do through a name is one of two kinds of action:

<Columns min={240}>
<div style={{ border: '1.5px solid var(--viz-2)', borderRadius: 12, padding: '0.1rem 1rem' }}>

**Mutate:** the object itself changes, so **every** name pointing at it sees the change.

- `b.append(3)`
- `b[0] = 9`
- `b.sort()`
- `b += [3]` (on a list)

</div>
<div style={{ border: '1.5px solid var(--viz-1)', borderRadius: 12, padding: '0.1rem 1rem' }}>

**Rebind:** only this name's arrow moves to another object. Other names keep the old object.

- `b = [9]`
- `b = b + [3]`
- `y = y + 1`

</div>
</Columns>

Two names that point at the same object are <Term def="Two or more names that refer to the same object. Mutating it through one name is visible through all of them.">aliases</Term>. Aliasing only bites with <Term def="Objects that can be changed after they are created: list, dict, set, and also NumPy arrays and PyTorch tensors.">mutable</Term> objects such as lists and dicts. Ints, floats, strings and tuples are <Term def="Objects that can never change once created: int, float, str, tuple, bool, None. Any 'change' really builds a new object.">immutable</Term>: every "change" builds a new object and moves one arrow, as the "ints" program showed.

<Note title="Watch out for +=">
On a list, `b += [3]` mutates the list in place (aliases see it), while `b = b + [3]` builds a new list and rebinds only `b`. On an int, `y += 1` can only rebind, because ints cannot change.
</Note>

When you really want a separate list, ask for a copy: `b = a.copy()` (or `list(a)`, or `a[:]`).

<Mistake title="Saving the 'best' weights with =">
A training loop keeps the best weights so far, then carries on updating. If you save them with `=`, you save an arrow to the live array, and the in-place update `-=` changes your "best" too:

```python
import numpy as np
w = np.array([1.0, 2.0])
best_w = w     # alias, not a copy
w -= 0.1 * np.array([10.0, 10.0])  # in place
print(best_w)
```

```text
[0. 1.]
```

Write `best_w = w.copy()` instead. PyTorch has the same trap: `model.state_dict()` refers to the live weight tensors, so a saved snapshot needs `copy.deepcopy(model.state_dict())`.
</Mistake>

<Note title="Copies are shallow">
`a.copy()` copies the outer list only. If the list holds other lists, the copy points at the same inner lists. `copy.deepcopy(a)` copies all the way down:

```python
import copy
a = [[1, 2], [3]]
b = a.copy()
b[0].append(9)   # inner list is shared
print(a)         # [[1, 2, 9], [3]]
c = copy.deepcopy(a)
c[0].append(7)   # c has its own
print(a)         # [[1, 2, 9], [3]]
```
</Note>

## Same value or same object?

Python has two different questions for "are these the same?":

- `a == b` asks whether they have **equal values**. Lists are compared item by item, in order.
- `a is b` asks whether they are the **very same object**, that is, whether both arrows end at one object.

Every object carries an <Term def="A number that identifies an object while it exists; no two live objects share one. id(x) returns it (in CPython it is the memory address).">identity</Term>, which the built-in `id(x)` returns. `a is b` is True exactly when `id(a) == id(b)`.

<Analogy title="Identical twins">
Identical twins look the same (`==` is True), but they are two different people (`is` is False). And you are always `is` yourself.
</Analogy>

<IdentityVsEquality />

<KeyIdea>
`==` compares **contents**; `is` compares **arrows**. Two names for one object normally hold equal values, so `a is b` being True means `a == b` is True as well. The reverse fails: equal lists are often separate objects.
</KeyIdea>

Use `is` mainly for `None`: write `if x is None:`. There is only ever one `None` object, so asking "is this that object?" is exactly the right test.

<Mistake title="Using is to compare numbers or strings">
`if score is 100:` may seem to work, because CPython reuses some small int and string objects, and then fail for other values. Python 3.8 and later even warns `SyntaxWarning: "is" with 'int' literal. Did you mean "=="?`. Compare values with `==`.
</Mistake>

## Passing a list into a function

When you call a function, each parameter is pointed at the argument's object, exactly as if you had written `scores = marks`. No copy is made. So the function can **mutate** your list, but if it **rebinds** its own parameter, only its local arrow moves.

<Analogy title="Lending your notebook">
You lend a friend your notebook. If they write in it, the writing is in **your** notebook when it comes back. If instead they put yours aside and write in a new notebook of their own, yours comes back clean.
</Analogy>

<FunctionMutationTrace />

This rule is called <Term def="Python's way of passing arguments: the parameter becomes a new name for the very object the caller passed, so mutations are shared but rebinding the parameter is not.">pass by object reference</Term> (or "call by sharing"). MCQ options often say "passed by reference", which is close enough: the fact that matters is that **no copy is made**.

<Mistake title="x = x.sort()">
`list.sort()` sorts the list in place and returns `None`. So `nums = nums.sort()` sorts the list and then points `nums` at `None`. Either call `nums.sort()` on its own line, or write `nums = sorted(nums)`, which returns a new sorted list. The same habit applies to your own functions: either change the input or return a new result, and make it clear which one you do.
</Mistake>

## The mutable default argument trap

A <Term def="A value written in the def line, as in def f(x, lr=0.1), that is used when the caller leaves that argument out.">default argument</Term> lets the caller leave an argument out. The catch: Python works out the default value **once, when the `def` line runs**, and stores that object on the function. Every call that relies on the default gets an arrow to that one stored object.

<Analogy title="The sign-up sheet at the counter">
A shop leaves one sign-up sheet at the counter. Every customer writes on the same sheet instead of getting a fresh one, so after three customers the "blank" form already has three names on it.
</Analogy>

<DefaultArgTrap />

Now trace a trickier version by hand. What are the four printed lines?

```python
def add_item(x, items=[]):
    items.append(x)
    return items

print(add_item(1))
print(add_item(2))
print(add_item(3, []))
print(add_item(4))
```

<Steps title="Tracing the four calls">
  <Step title="The def line runs">
    One empty list is created and stored as the default. Call it D.
  </Step>
  <Step title="Calls 1 and 2 share D">
    `add_item(1)` appends to D, printing `[1]`. `add_item(2)` appends to the same D, printing `[1, 2]`.
  </Step>
  <Step title="Call 3 brings its own list">
    `add_item(3, [])` passes a brand-new empty list, so `items` points at that list, not D. It prints `[3]`, and D is untouched.
  </Step>
  <Step title="Call 4 is back on D">
    `add_item(4)` leaves `items` out again, so it gets D, which still holds `[1, 2]`. It prints `[1, 2, 4]`.
  </Step>
</Steps>

The fix uses the `is None` test from earlier. Store `None`, which can never change, and build a fresh list inside each call:

```python
def add_item(x, items=None):
    if items is None:  # no list given
        items = []
    items.append(x)
    return items

print(add_item(1))
print(add_item(2))
```

```text
[1]
[2]
```

## What happens to objects nobody points at?

In the function visual, the list built by `scores = scores + [100]` faded out when the function ended. CPython does this with <Term def="Each object keeps a count of how many references point to it. Every new arrow adds 1, every removed arrow subtracts 1, and at 0 the object is freed at once.">reference counting</Term>: every object counts the arrows pointing at it, and the moment the count reaches 0, its memory is freed.

Counting has one blind spot. Two objects that point at each other (a cycle) keep each other's counts above 0 even when no name can reach them. So Python also runs a **cyclic garbage collector** now and then to find and free such islands.

<Takeaways>
- A name is an arrow to an object. `=` moves arrows and never copies objects.
- Mutating an object (`.append`, `x[i] = …`, `+=` on a list) is seen through every name that points at it; rebinding a name is not.
- `==` compares values; `is` compares identity (same object). Use `is` for `None` checks only.
- A function receives an arrow to your list, not a copy, so it can mutate your list.
- Defaults are created once, when `def` runs: use `items=None` and build the list inside.
</Takeaways>
