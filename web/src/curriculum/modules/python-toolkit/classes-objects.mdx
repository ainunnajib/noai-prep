Every model in this course is an **object**. `model = LinearRegression()` builds one, `model.fit(X, y)` teaches it, and `model.predict(X)` uses what it learned. In PyTorch you will write `class Net(nn.Module):` before you write a single layer. This lesson shows what those lines really mean, so that exam code full of `self.` reads like plain English.

## A class is a blueprint, an object is the thing built

<Analogy title="BTO floor plans and flats">

HDB draws one floor plan for a block of BTO flats. The plan is not a home: nobody lives in it. But from that one plan, hundreds of real flats are built, each with the same layout and a different family inside. A **class** is the floor plan; each **object** is a real flat.

</Analogy>

The words you need:

- A <Term def="A blueprint for a new type of object: it lists the data each object will store and the functions each object can run.">class</Term> describes a new type of thing. It is made with the `class` keyword.
- An <Term def="One concrete thing built from a class, with its own data. 'Object' and 'instance' mean the same thing.">object</Term>, also called an **instance**, is one thing built from the class.
- An <Term def="A named value stored on an object, read and written with a dot: s1.score.">attribute</Term> is a value stored on an object, such as `s1.score`.
- A <Term def="A function defined inside a class. You call it on an object with a dot, and it receives that object as its first parameter, self.">method</Term> is a function that belongs to the class, called with a dot: `s1.passed()`.

```python
class Student:
    def __init__(self, name, score):
        self.name = name   # attribute
        self.score = score

    def passed(self):
        return self.score >= 50

s1 = Student("Aisha", 81)
s2 = Student("Ben", 45)
print(s1.name, s1.passed())
print(s2.name, s2.passed())
```

```text
Aisha True
Ben False
```

### What `Student("Aisha", 81)` actually does

<Steps title="Building one object">
  <Step title="Make an empty object">
    Python creates a new, empty `Student` object. It has no `name` or `score` yet.
  </Step>
  <Step title="Call `__init__` on it">
    Python calls the special method `__init__` (say "dunder init", for the double underscores), the <Term def="The method Python runs automatically when you create an object; its job is to set up the object's starting attributes.">initialiser</Term> (often loosely called the constructor). It passes the new, already-made object as `self`, then your arguments: `name = "Aisha"`, `score = 81`.
  </Step>
  <Step title="Store attributes on self">
    `self.name = name` attaches an attribute to **this** object. Without the `self.` part, `name` would just be a local variable that vanishes when `__init__` ends.
  </Step>
  <Step title="Hand the object back">
    The finished object is returned, and the name `s1` points at it (an arrow, as in the previous lesson).
  </Step>
</Steps>

When you later call `s1.passed()`, Python runs `Student.passed(s1)`. The object before the dot is passed in automatically as the first parameter, which by convention is named <Term def="The first parameter of every method: the object the method was called on. In s1.passed(), self is s1.">self</Term>. That is how one method, written once, can read the right `score` for every student.

<KeyIdea>

A class is written once; each object made from it keeps **its own** attributes. Inside a method, `self` is the object the method was called on: `s1.passed()` means `Student.passed(s1)`.

</KeyIdea>

<Mistake title="Forgetting self">

Two classic errors, both from leaving out `self`:

- Writing `name = name` instead of `self.name = name` in `__init__`. The value never reaches the object, and later `s1.name` fails with `AttributeError: 'Student' object has no attribute 'name'`.
- Writing `def passed():` with no `self` parameter. Calling `s1.passed()` still passes `s1` in, so you get `TypeError: Student.passed() takes 0 positional arguments but 1 was given`.

</Mistake>

## Methods that remember: the fit/predict pattern

Attributes outlive method calls. A local variable disappears when its function returns, but an attribute stored on `self` stays on the object until something changes it. That is exactly what a machine learning model needs: **learn** something in one call, **use** it in a later one.

<Analogy title="Study, then answer from memory">

A student studies the notes (fit) and keeps what they learned in their head. In the exam they answer from memory (predict), without the notes. Asking for answers before studying gets you nothing useful.

</Analogy>

Here is the simplest possible model. It learns the mean of the training targets and predicts that mean for every input.

```python
class MeanPredictor:
    def fit(self, y):
        self.mean_ = sum(y) / len(y)  # learn
        return self

    def predict(self, X):
        return [self.mean_ for x in X]  # use

model = MeanPredictor()
model.fit([2, 4, 9])
print(model.mean_)
print(model.predict([10, 20]))
```

```text
5.0
[5.0, 5.0]
```

<ObjectStateInspector />

Three details are copied straight from scikit-learn:

- `fit` **changes the object** (its <Term def="The current values of an object's attributes. Methods can read and change it; it persists between calls.">state</Term>), and `predict` only **reads** it.
- Attributes learned from data end in an underscore, like `mean_`. In scikit-learn you will meet `coef_`, `intercept_` and `classes_`.
- `fit` returns `self`, so you can chain calls: `MeanPredictor().fit([10, 20]).predict([1, 2, 3])` gives `[15.0, 15.0, 15.0]`.

scikit-learn even ships this model, as `DummyRegressor`. It is a useful baseline: any real model should beat it.

<PyRunner packages={['scikit-learn']} code={`from sklearn.dummy import DummyRegressor

X = [[1], [2], [3]]   # inputs (ignored)
y = [2, 4, 9]         # targets
model = DummyRegressor(strategy="mean")

print(model.predict([[10], [20]]))`} />

`constant_` prints as `[[5.]]` rather than `5.0`: scikit-learn stores it as a small NumPy array, with one value per target column. The mean is the same 5.0 that `MeanPredictor` learned.

<Mistake title="A list at class level is shared by every object">

Attributes should be created on `self` inside `__init__`. A list written directly in the class body belongs to the class, so every object shares it, the same trap as a mutable default argument:

```python
class Bag:
    items = []     # ONE list, on the class
    def add(self, x):
        self.items.append(x)

p = Bag()
q = Bag()
p.add("pen")
print(q.items)     # ['pen'] !
```

Write `def __init__(self): self.items = []` so each bag gets its own list.

</Mistake>

<ExamTip>

NOAI Final tasks are scaffolds: a class with `__init__` already written and empty methods for you to fill in. **Read `__init__` first.** It tells you the exact attribute names (`self.trees`, `self.init_prediction`, `self.learning_rate`) that your `fit` must fill and your `predict` must read. Hidden tests call those names, so keep every given name and signature exactly as provided.

</ExamTip>

## Inheritance: reuse a parent class

Often a new class is "like that one, except…". <Term def="Making a new class (the child, or subclass) from an existing one (the parent, or base class). The child gets all the parent's methods and can override some of them.">Inheritance</Term> lets a child class start with **everything** the parent has and change only what differs.

<Analogy title="A new hawker stall">

A hawker opens a second stall with the parent stall's recipes. Rice, sauce and soup stay the same; only the chilli is changed. Customers ordering soup get the parent recipe; customers asking for chilli get the new one.

</Analogy>

```python
class Model:
    def __init__(self, name):
        self.name = name

    def fit(self, X, y):
        self.trained = True

    def kind(self):
        return "generic model"

    def describe(self):
        return self.name + ": " + self.kind()

class Baseline(Model):  # inherits Model
    def kind(self):     # override kind
        return "mean baseline"

b = Baseline("b1")
b.fit([[1]], [2])
print(b.trained)
print(b.describe())
```

```text
True
b1: mean baseline
```

`Baseline` never defines `__init__`, `fit` or `describe`, yet `b` can use all three. When you call a method, Python searches the object's own class first, then the parent, then the parent's parent, and runs the **first** match. A child method with the same name as a parent method <Term def="Defining a method in a child class with the same name as one in the parent, so the child's version is found first.">overrides</Term> it.

<InheritanceTree />

The surprising part is `b.describe()`. Its code lives in `Model`, but inside it `self` is still `b`, a `Baseline`, so `self.kind()` starts the search at `Baseline` again and finds the override. Parent code calling `self.something()` automatically uses the child's version. That is how a framework can run **your** code.

### `super()`: let the parent set itself up

If a child defines its own `__init__`, it replaces the parent's. To keep the parent's setup as well, call it through <Term def="A built-in that gives you the parent class's version of a method, e.g. super().__init__(name) runs the parent's __init__ on this object.">super()</Term>:

```python
class Baseline(Model):
    def __init__(self, name, strategy):
        super().__init__(name)  # Model's setup
        self.strategy = strategy  # child's own
```

### This is exactly how PyTorch models work

Every PyTorch model is a subclass of `nn.Module`. You override two methods: `__init__` to create the layers, and `forward` to say what the network computes. `nn.Module`'s own methods, inherited for free, do the rest: `net(x)` runs your `forward`, and `net.parameters()` finds every weight.

```python
import torch
import torch.nn as nn

class TinyNet(nn.Module):
    def __init__(self):
        super().__init__()  # nn.Module setup
        self.layer = nn.Linear(2, 1)  # a layer

    def forward(self, x):  # what net computes
        return self.layer(x)

net = TinyNet()
x = torch.tensor([[1.0, 2.0]])
print(net(x).shape)  # net(x) runs forward
print(sum(p.numel() for p in net.parameters()))
```

```text
torch.Size([1, 1])
3
```

The 3 parameters are the two weights and one bias of `nn.Linear(2, 1)`, found automatically because the layer was stored on `self`. Forget the `super().__init__()` line and PyTorch stops you at once: `AttributeError: cannot assign module before Module.__init__() call`.

<Note title="Special methods hook into Python's syntax">

Methods with double underscores on both sides are called by Python itself when you use ordinary syntax on an object. `len(obj)` calls `obj.__len__()`, `obj[i]` calls `obj.__getitem__(i)`, and `obj(x)` calls `obj.__call__(x)`. That is why `net(x)` works: `nn.Module` defines `__call__`, which runs your `forward`. A PyTorch `Dataset` class you write yourself defines `__len__` and `__getitem__`, so that `len(dataset)` and `dataset[i]` work.

</Note>

## Abstract base classes: templates with blanks

Sometimes a parent class is not meant to be used on its own. It holds the shared code and leaves some methods as **blanks** that every child must fill in. That is an <Term def="A class that cannot be instantiated itself; it declares abstract methods that every concrete subclass must implement, and usually provides shared code that uses them.">abstract base class</Term> (ABC).

<Analogy title="A form with must-fill boxes">

A government form has some boxes pre-printed and others marked "must fill in". Every copy shares the printed parts. A form with an empty must-fill box is rejected at the counter, before anyone tries to process it.

</Analogy>

The example below is a **loss**, which scores how wrong a prediction is. It has two jobs: `value(y, p)` measures how wrong the prediction `p` is for the target `y`, and `gradient(y, p)` says which way, and how far, to nudge `p` to make it less wrong. Every kind of loss needs both, but each one works them out differently, so they are left as blanks.

```python
from abc import ABC, abstractmethod

class Loss(ABC):
    @abstractmethod
    def value(self, y, p): ...     # blank

    @abstractmethod
    def gradient(self, y, p): ...  # blank

    def step(self, y, p, lr):  # shared
        return p - lr * self.gradient(y, p)

class L2Loss(Loss):
    def value(self, y, p):
        return (p - y) ** 2 / 2

    def gradient(self, y, p):
        return p - y
```

Reading it line by line:

- `class Loss(ABC)` inherits from `ABC`, which switches on the "check for blanks" rule.
- `@abstractmethod` is a <Term def="A tag written with @ on the line above a def. It passes the function through another function that changes or labels it.">decorator</Term>: a tag above a `def`. It marks the method as a blank. The body `...` is Python's placeholder for "no code here".
- `step` is an ordinary method. It is written once and calls `self.gradient(...)`, trusting each child to supply it, as `describe` trusted `kind` above.
- Python refuses to create an object while any abstract method is still blank, so `Loss()` fails. So does a child that forgets one, raising `TypeError` the moment you create it rather than halfway through training.

<AbstractTemplate />

Check the numbers for `L2Loss().step(5, 2, 0.5)`: the gradient is $p - y = 2 - 5 = -3$, so the step returns $2 - 0.5 \times (-3) = 3.5$. The prediction moved from 2 towards the target 5.

The visual's second child, `L1Loss`, fills the same blanks differently. Its value is `abs(p - y)`, and its gradient is just the **sign** of $p - y$: `return (p > y) - (p < y)`. True counts as 1 and False as 0, so this gives $+1$ when the prediction is too big, $-1$ when it is too small, and $0$ when it is exactly right (the same as `np.sign(p - y)`).

Here $p < y$, so the gradient is $-1$ and `step` gives $2 - 0.5 \times (-1) = 2.5$: a smaller nudge in the same direction. The shared `step` code did not change at all.

<KeyIdea>

In an abstract base class, the methods marked `@abstractmethod` are the blanks. They tell you exactly what a subclass, or an exam scaffold, expects you to write. The concrete methods are shared code you can rely on but should not rewrite.

</KeyIdea>

<ExamTip>

The 2026 NOAI Final's gradient-boosting task used this exact pattern: `BaseGradientBoosting(ABC)` held shared helpers and marked `fit` as abstract, and `GradientBoostingRegressor(BaseGradientBoosting)` had to implement it. When a scaffold arrives, scan for `@abstractmethod` and for empty bodies first: that list is your to-do list.

</ExamTip>

<Takeaways>

- A class is a blueprint; each object (instance) has its own attributes, set up in `__init__` on `self`.
- In `obj.method()`, Python passes `obj` in as `self`, so one method works for every object.
- `fit` stores what was learned on `self` (like `mean_`); `predict` reads it. Calling `predict` first fails.
- A child class inherits all its parent's methods, overrides the ones that differ, and calls `super().__init__()` to keep the parent's setup. `class Net(nn.Module)` with `forward` is exactly this.
- An abstract base class marks blanks with `@abstractmethod`; you cannot create an object until every blank is filled.

</Takeaways>
