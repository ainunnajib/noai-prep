def smote(X_min, n_new, k=3, seed=0):
    """Make n_new synthetic minority points by interpolating between neighbours."""
    rng = np.random.default_rng(seed)
    # distance from every minority point to every other one
    d = np.linalg.norm(X_min[:, None, :] - X_min[None, :, :], axis=2)
    np.fill_diagonal(d, np.inf)                  # a point is not its own neighbour
    neighbours = np.argsort(d, axis=1)[:, :k]    # k nearest, row by row
    new = np.empty((n_new, X_min.shape[1]))
    for s in range(n_new):
        i = rng.integers(len(X_min))             # pick a minority point
        j = neighbours[i, rng.integers(k)]       # and one of its k neighbours
        lam = rng.random()                       # a random number in [0, 1)
        new[s] = X_min[i] + lam * (X_min[j] - X_min[i])
    return new

X_fraud = np.array([[2.0, 1.0], [2.5, 2.0], [3.0, 1.5], [1.5, 2.5]])

Fraudulent card payments, a rare disease in a screening programme, a faulty chip on a production line: in many of the most useful AI problems, the thing you are hunting for is **rare**. Rarity breaks the usual scorecard. A model can look 99% accurate while being completely useless, and the standard training recipe quietly learns to ignore the rare class. This lesson shows why, how to measure honestly, and the standard fixes.

<Analogy title="The security guard who never stops anyone">

A shopping centre on Orchard Road has 1,000 visitors an hour and, on a bad day, one shoplifter. A guard who simply waves everyone through is "right" about 999 of the 1,000 visitors, a 99.9% success rate. He has also caught exactly zero thieves. Counting how often he is right says nothing about whether he is doing his job.

</Analogy>

## When one class is rare

A dataset has <Term def="When one class is much more common than the other, for example 98% genuine payments and 2% fraud.">class imbalance</Term> when one class vastly outnumbers the other. The common class is the <Term def="The class with many more examples (e.g. genuine payments).">majority class</Term>; the rare one, usually the class we care about and label positive (1), is the <Term def="The class with few examples, usually the positive class we want to detect (e.g. fraud).">minority class</Term>. The fraction of examples that are positive is called the <Term def="The fraction of all examples that are positive, also called the base rate. 2% prevalence means 2 in every 100 examples are positive.">prevalence</Term> (or base rate).

## The accuracy paradox

Take the laziest possible model: it predicts "negative" for everything. It is right on every negative and wrong on every positive, so its accuracy is just the share of negatives:

$$
\text{accuracy} = 1 - \text{prevalence}
$$

With 1% fraud, that is 99% accuracy, from a model that has never caught a single fraud (recall 0). Slide the fraud rate down in the figure below and watch accuracy climb while the model stays useless.

<AccuracyParadox />

It gets worse. A genuinely useful model can score **lower** accuracy than the useless one. This is the <Term def="The situation where a useless model (for example, one that always predicts the majority class) has higher accuracy than a genuinely useful model, because the classes are imbalanced.">accuracy paradox</Term>.

<Steps title="10,000 payments, 1% fraud, a real detector">
  <Step title="Split the payments">
    1% of 10,000 is **100 frauds**; the other **9,900 are genuine**.
  </Step>
  <Step title="Apply the detector">
    It catches 80% of frauds: $TP = 80$, $FN = 20$. It raises a false alarm on 5% of genuine payments: $FP = 0.05 \times 9{,}900 = 495$, so $TN = 9{,}405$.
  </Step>
  <Step title="Accuracy">
    $\frac{80 + 9{,}405}{10{,}000} = 0.9485$, about 94.9%. The "always genuine" model scores $\frac{9{,}900}{10{,}000} = 99\%$. By accuracy, the useless model wins!
  </Step>
  <Step title="The metrics that tell the truth">
    Recall $= \frac{80}{100} = 0.80$ (versus 0 for the lazy model). Precision $= \frac{80}{80 + 495} \approx 0.14$: only about 1 in 7 alarms is real fraud. F1 $= \frac{2 \times 80}{160 + 495 + 20} \approx 0.24$.
  </Step>
</Steps>

<KeyIdea>

When classes are imbalanced, **accuracy is misleading**: it is dominated by the easy majority class. Judge the model on the rare class instead: its **recall**, **precision** and **F1**, or the precision-recall curve (next lesson).

</KeyIdea>

One more honest summary is <Term def="The average of the recall of each class: (recall + specificity) / 2 for two classes. A model that always predicts one class scores 0.5.">balanced accuracy</Term>, the average of the recall of each class, $\frac{\text{recall} + \text{specificity}}{2}$. The "always negative" model gets $\frac{0 + 1}{2} = 0.5$, no better than a coin, which is exactly what it deserves.

## Why models ignore the rare class

Training minimises the **average** loss over all examples. With 98% genuine payments, 98% of the terms in that average are about genuine payments. The cheapest way to make the average small is to push every score towards "genuine": the model learns that fraud is almost never the answer, and at the default threshold of 0.5 it hardly ever predicts it.

So there are three places to intervene: change the **loss** (make each rare example count more), change the **data** (make the rare class less rare in training), or change the **decision** (lower the threshold). Explore all of them below.

<ImbalanceRemedies />

### Class weights: change the loss

Give each example's loss a weight $w$ that depends on its class, and minimise

$$
L = \frac{1}{N}\sum_{i=1}^{N} w_{y_i}\, \ell_i
$$

Here $N$ is the number of training examples, $\ell_i$ is the ordinary loss of example $i$ (for example its cross-entropy), and $w_{y_i}$ is the weight of its class $y_i$. A common choice is $w_0 = 1$ for the majority class and $w_1 = \frac{n_0}{n_1}$ for the minority class, where $n_0$ and $n_1$ are the class sizes. With 9,800 genuine and 200 fraud payments, $w_1 = \frac{9{,}800}{200} = 49$: every missed fraud now costs 49 times as much, so the 200 frauds weigh as much in total as the 9,800 genuine payments. In scikit-learn, `class_weight={0: 1, 1: 49}` sets exactly these weights, and `class_weight="balanced"` sets $w_c = \frac{n}{2 n_c}$ (here about 0.51 and 25), the same 49 : 1 ratio. In PyTorch it is the `pos_weight` or `weight` argument of the loss (code below).

### Resampling: change the data

**Random oversampling.** <Term def="Duplicating randomly chosen minority examples until the classes are (closer to) balanced.">Random oversampling</Term> copies minority examples until the classes balance. Repeating each fraud so that it appears 49 times (48 extra copies) has the same effect on the loss as giving it weight 49, but the dataset grows and the model sees the same few rows over and over, which encourages memorising them.

**SMOTE.** <Term def="Synthetic Minority Over-sampling TEchnique: creates new minority examples on the straight line between a minority example and one of its k nearest minority neighbours.">SMOTE</Term> (Synthetic Minority Over-sampling Technique) invents *new* minority points instead of copies. For a minority point $x_i$, pick one of its $k$ nearest minority neighbours $x_{nn}$ (the same "nearest neighbours" as in k-NN) and a random number $\lambda$ between 0 and 1. The new point is

$$
x_{\text{new}} = x_i + \lambda\,(x_{nn} - x_i)
$$

a point on the straight line from $x_i$ to $x_{nn}$: $\lambda = 0$ gives $x_i$ itself, $\lambda = 1$ gives the neighbour, $\lambda = 0.5$ the midpoint. SMOTE draws a fresh random $\lambda$ for each new point. In the visual, shrink the range of $\lambda$ to 0 and SMOTE turns into plain copying.

**Random undersampling.** <Term def="Randomly throwing away majority examples until the classes are (closer to) balanced.">Random undersampling</Term> throws away majority examples. It is fast, but it discards real information: balancing 9,800 genuine against 200 fraud payments means deleting 9,600 genuine ones.

### Threshold moving: change the decision

You can also leave training alone and **lower the threshold**, exactly as in the previous lesson. For a well-behaved model, weighting the positives by $w$ has roughly the same effect as lowering the threshold to $\frac{1}{1 + w}$. With $w = 49$ that is $\frac{1}{50} = 0.02$, the fraud rate itself. The code at the end of the lesson shows the two giving almost identical results. (The visual uses 5% fraud, 12 frauds against 228 genuine payments, so there the weight is $228 \div 12 = 19$ and the matching threshold $\frac{1}{20} = 0.05$.)

| remedy | what changes | main risk |
|---|---|---|
| class weights | the loss (data unchanged) | scores stop being honest probabilities |
| random oversampling | the data: more rows (copies) | memorising duplicated rows; slower |
| SMOTE | the data: more rows (synthetic) | unrealistic points where classes overlap |
| random undersampling | the data: far fewer rows | throws away information; unstable |
| lower threshold | the decision only | needs a validation set to choose it |

Every remedy moves the model along the same precision-recall trade-off: more frauds caught, more false alarms. None of them creates information that was not in the data.

<Mistake title="Resample after splitting, and never touch the test set">

Split into training and test sets **first**, then resample only the training set. If you oversample (or run SMOTE) before splitting, copies of the same fraud, or synthetic points built from it, land in both sets, and the test score is inflated by leakage. The test set must keep the real-world imbalance: that is the situation the model will face.

</Mistake>

## Choosing the metric by cost

<Analogy title="A smoke alarm">

Set a smoke alarm too sensitive and it shrieks every time you fry ikan bilis. Set it too lax and it stays quiet during a real fire. Where you set it depends on what each mistake costs: a few annoyed neighbours versus a burnt flat.

</Analogy>

When you can put a price on each mistake, the best threshold follows from a two-line calculation. Suppose a **calibrated** model says a payment is fraud with probability $p$. (A model is <Term def="A model whose probabilities match reality: of all the cases it gives probability 0.1, about 10% really are positive.">calibrated</Term> when its probabilities can be taken at face value.) Let $c_{FP}$ be the cost of a false alarm and $c_{FN}$ the cost of a missed fraud.

- If you **flag** the payment, you pay $c_{FP}$ only if it was genuine, which happens with probability $1 - p$. Expected cost: $(1 - p)\,c_{FP}$.
- If you **let it through**, you pay $c_{FN}$ only if it was fraud, with probability $p$. Expected cost: $p\,c_{FN}$.

Flag it when that is cheaper: $(1 - p)\,c_{FP} < p\,c_{FN}$. Rearranging gives the best threshold

$$
t^* = \frac{c_{FP}}{c_{FP} + c_{FN}}
$$

Flag every payment with $p > t^*$. When misses are expensive ($c_{FN}$ large), $t^*$ is small: you flag almost anything suspicious.

<Steps title="A bank: a false alarm (phoning about a genuine payment) costs 10 dollars, a missed fraud 90 dollars">
  <Step title="Best threshold">
    $t^* = \frac{10}{10 + 90} = 0.1$. Flag anything the model rates above a 10% chance of fraud.
  </Step>
  <Step title="A payment with p = 0.2">
    Flag: $(1 - 0.2) \times 10 = \$8$. Let through: $0.2 \times 90 = \$18$. Flagging is cheaper, as the rule says ($0.2 > 0.1$).
  </Step>
  <Step title="A payment with p = 0.05">
    Flag: $0.95 \times 10 = \$9.50$. Let through: $0.05 \times 90 = \$4.50$. Let it through ($0.05 < 0.1$).
  </Step>
</Steps>

<CostMatrixSlider />

In the visual, the threshold 0.1 catches 165 of the 200 frauds and costs \$5,060 per 10,000 payments, while the default 0.5 catches only 116 and costs \$7,810, even though its **accuracy is higher** (0.989 against 0.977). Accuracy rewards the wrong thing again.

<Note title="For the curious: other cost set-ups">
The formula charges $c_{FP}$ only when a flagged payment turns out to be genuine. If instead a check costs $c$ on **every** flagged payment, fraud or not, flagging always costs $c$, so you flag when $c < p\,c_{FN}$: the threshold is $c / c_{FN}$ (here $10/90 \approx 0.11$).
</Note>

<KeyIdea>

Match the metric to the cost of mistakes. When misses are expensive (fraud, disease), prioritise **recall**, but watch **precision** so the alarms do not swamp the people who must check them. Report a threshold-free summary such as **<Term def="The area under the precision-recall curve, also called average precision: one number that summarises how well the model finds the rare class across all thresholds. It is taught in the next lesson.">PR-AUC</Term>** (next lesson), *plus* the operating point you chose: its threshold, precision, recall and the F1 at that threshold. (F1 is not threshold-free: it comes from one confusion matrix, so it changes when the threshold moves.)

</KeyIdea>

| scenario (positive class) | prioritise | why |
|---|---|---|
| card fraud (fraud) | recall, with a minimum precision | a miss loses money; too many alarms swamp investigators |
| rare-disease screening (disease) | recall | a missed patient goes untreated; a false alarm costs a follow-up test |
| confirming a diagnosis before surgery (disease) | precision | a false positive means an unnecessary operation |

When a miss costs far more than a false alarm, and alarms can be reviewed, recall (with a floor on precision) is the main metric. F1 weighs precision and recall equally, so it is not automatically the safe answer, and ROC-AUC (next lesson) can look flattering when positives are rare.

Class weights lift recall from 0.42 to 0.90, but F1 falls from 0.51 to 0.23: reweighting buys recall with precision. Whether that trade is worth it depends on the costs, not on F1.

In PyTorch, the weight goes into the loss function. `BCEWithLogitsLoss` takes `pos_weight` (multiply the loss of every positive example); `CrossEntropyLoss` takes one `weight` per class.

```python
import torch
import torch.nn as nn

logits  = torch.tensor([2.0, -1.0, -2.0, 0.5])   # raw model outputs for 4 payments
targets = torch.tensor([1.0,  0.0,  1.0, 0.0])   # 1 = fraud

plain    = nn.BCEWithLogitsLoss()
weighted = nn.BCEWithLogitsLoss(pos_weight=torch.tensor([49.0]))  # 9,800 / 200

print(f"plain loss:    {plain(logits, targets).item():.4f}")
print(f"weighted loss: {weighted(logits, targets).item():.4f}")

# the same weighting for a 2-class model with CrossEntropyLoss
ce = nn.CrossEntropyLoss(weight=torch.tensor([1.0, 49.0]))
two_class_logits = torch.tensor([[0.0, 2.0], [0.0, -1.0], [0.0, -2.0], [0.0, 0.5]])
print(f"weighted CE:   {ce(two_class_logits, targets.long()).item():.4f}")
```

```text
plain loss:    0.8853
weighted loss: 27.9316
weighted CE:   1.1173
```

The weighted loss is much larger because the two frauds' losses (0.127 and 2.127) are each multiplied by 49 before averaging over the 4 payments. `CrossEntropyLoss` with `weight` divides by the **total weight** ($49 + 1 + 49 + 1 = 100$) instead of by 4, so its number is smaller, but the balance between the classes is the same.

<Takeaways>

- With rare positives, "always negative" scores accuracy $= 1 - \text{prevalence}$ and recall 0: **accuracy is misleading** (the accuracy paradox).
- Judge the rare class with **recall, precision, F1** (or PR-AUC, balanced accuracy), never accuracy alone.
- **Class weights** change only the loss ($w_1 = n_0 / n_1$, e.g. 49 for 2% fraud) and are the usual first choice; **oversampling** copies, **SMOTE** interpolates $x_i + \lambda(x_{nn} - x_i)$, **undersampling** discards; **lowering the threshold** changes only the decision.
- Resample only the training set, after splitting; evaluate on data with the real imbalance.
- With costs $c_{FP}$ and $c_{FN}$ and calibrated probabilities, the best threshold is $t^* = \frac{c_{FP}}{c_{FP} + c_{FN}}$.

</Takeaways>
