    m, n = len(a), len(b)
    D = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(m + 1):
        D[i][0] = i      # deletes

Some problems are easiest to solve by first solving a smaller copy of the same problem. This lesson covers three ideas built on that thought: **recursion** (a function that calls itself), **dynamic programming** (remember the answers to smaller problems so you never solve one twice) and **graph search** (explore a network of connected things, breadth-first or depth-first). They sit underneath spell-checkers, route planners, speech recognisers and even backpropagation, and NOAI asks you to trace them by hand.

## Recursion: a function that calls itself

<Analogy title="What's my place in the queue?">

You join a long queue at a popular hawker stall and want to know your position. Instead of walking to the front to count, you ask the person in front of you: "what's your position?" They don't know either, so they ask the person in front of them, and so on. The person at the very front simply knows: "I'm number 1." Then the answers flow back: 2, 3, 4, … until you hear yours. Each person solved a smaller version of your question and added one.

</Analogy>

A <Term def="A function that solves a problem by calling itself on a smaller version of the same problem.">recursive function</Term> calls itself on a smaller input. It needs two parts:

- a <Term def="The input small enough to answer directly, without another recursive call. It stops the recursion.">base case</Term>: an input so small that the answer is known directly (the person at the front of the queue);
- a **recursive case**: the answer for $n$ built from the answer for a smaller input (ask the person in front, then add one).

The factorial $n! = n \times (n-1) \times \dots \times 1$, with $0! = 1$, is the classic example:

```python
def factorial(n):
    if n == 0:        # base case
        return 1
    # recursive case
    return n * factorial(n - 1)
```

<Steps title="Trace factorial(3)">
  <Step title="Going down: the calls">
    `factorial(3)` needs `3 * factorial(2)`, so it waits and calls `factorial(2)`, which waits and calls `factorial(1)`, which waits and calls `factorial(0)`.
  </Step>
  <Step title="The base case">
    `factorial(0)` returns 1 at once. Four calls are now on the <Term def="The list of function calls that have started but not finished yet. Each waiting call keeps its own variables in a frame on the stack.">call stack</Term>, three of them still waiting.
  </Step>
  <Step title="Coming back up: the returns">
    `factorial(1)` returns $1 \times 1 = 1$, then `factorial(2)` returns $2 \times 1 = 2$, then `factorial(3)` returns $3 \times 2 = 6$.
  </Step>
  <Step title="Cost">
    $n + 1$ calls, each doing $O(1)$ work: $O(n)$ time. But all $n + 1$ calls sit on the stack at the deepest point, so recursion also uses $O(n)$ **space**.
  </Step>
</Steps>

Without a base case, or with a recursive call that doesn't get closer to it (such as `factorial(n + 1)`), the calls never stop. Python gives up after about 1,000 nested calls with `RecursionError: maximum recursion depth exceeded`.

</Mistake>

## Fibonacci: when recursion repeats itself

The Fibonacci numbers $0, 1, 1, 2, 3, 5, 8, 13, \dots$ are defined recursively: each is the sum of the two before it.

$$
F(n) = F(n-1) + F(n-2)
$$

Here $F(n)$ is the $n$-th Fibonacci number, and the two starting values $F(0) = 0$ and $F(1) = 1$ are the base cases. The Python is a direct copy:

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)
```

It is correct, but each call makes **two** more calls, so the calls form a tree. Look at how often the same question gets asked:

<FibRecursionTree />

`fib(6)` calls `fib(2)` five separate times and `fib(1)` eight times, recomputing answers it has already found. The number of calls is $2F(n+1) - 1$, which grows by a factor of about 1.6 for each step up in $n$: exponential, roughly $O(1.6^n)$ (so certainly $O(2^n)$). `fib(30)` needs 2,692,537 calls; `fib(50)` would need over 40 billion.

## Memoisation: remember every answer

The repeated circles in the tree are <Term def="Smaller problems that come up again and again while solving the big one, like fib(2) inside fib(6).">overlapping subproblems</Term>, and they are the signal to cache. <Term def="Storing the answer to each function call the first time it is computed (usually in a dict), and looking it up instead of recomputing it next time.">Memoisation</Term> keeps a dict from input to answer: before computing, look the input up; after computing, store the answer.

<PyRunner code={memoCode} />

With the memo, each `fib(k)` is computed once; every later request is a dict lookup, which is $O(1)$ on average (last lesson). There are only $n + 1$ different subproblems, so memoised `fib(n)` makes $2n - 1$ calls: $O(n)$ time, plus $O(n)$ space for the memo. That is the difference between 242,785 calls and 49 for `fib(25)`. Python's `@lru_cache` decorator does the same bookkeeping for you.

<KeyIdea>

If a recursive solution solves the same subproblem more than once, store each answer the first time. Memoisation trades $O(n)$ memory for the jump from exponential to linear time.

</KeyIdea>

## Dynamic programming: fill a table in the right order

<Term def="Solving a problem by answering its smaller subproblems, storing each answer, and building bigger answers from stored ones.">Dynamic programming</Term> (DP) works when a problem has two properties: **optimal substructure** (the best answer is built from the best answers to smaller subproblems) and **overlapping subproblems** (the same subproblems come up again and again). Memoisation is **top-down** DP: start from the big problem and cache on the way. The other style is **bottom-up** DP, also called tabulation: answer the smallest subproblems first and fill a table in an order where every entry only needs entries already filled. Both give the same complexity, but bottom-up never runs into Python's recursion limit (a memoised `fib(2000)` raises `RecursionError`). For Fibonacci the table is a single row: $F(0), F(1), F(2), \dots$, each the sum of the two to its left.

<Analogy title="Cheapest MRT fares, station by station">

To plan the cheapest trip from your station to every other station, you don't try every possible route. You first find the cheapest cost to the nearby stations, then use those answers to work out the stations one step further, and so on. Each new answer is built from answers you already wrote down.

</Analogy>

Every DP solution answers the same five questions: **what is a subproblem**, **how is a subproblem built from smaller ones** (the recurrence), **what are the base cases**, **in what order do I fill the table**, and **where is the final answer**?

### Edit distance

The <Term def="The smallest number of single-letter insertions, deletions and substitutions needed to turn one word into another (also called Levenshtein distance).">edit distance</Term> between two words is the fewest single-letter edits (insert a letter, delete a letter, or substitute one letter for another) that turn one into the other. Spell-checkers use it to suggest "kitten" for "kiten", and speech recognisers are scored with it: the word error rate is the edit distance between the words heard and the true words, divided by the number of true words.

Turn word $a$ (length $m$) into word $b$ (length $n$). Let $D[i][j]$ be the edit distance between the **first $i$ letters** of $a$ and the **first $j$ letters** of $b$. Then

$$
D[i][j] = \min\begin{cases} D[i-1][j-1] + c \\ D[i-1][j] + 1 \\ D[i][j-1] + 1 \end{cases}
$$

The three lines are the three possible last edits, and each one leaves a smaller problem whose answer is already in the table:

- **up-left**, $D[i-1][j-1] + c$: substitute the $i$-th letter of $a$ by the $j$-th letter of $b$. Here $c = 0$ if the two letters are already equal (a free match) and $c = 1$ otherwise;
- **up**, $D[i-1][j] + 1$: delete the $i$-th letter of $a$;
- **left**, $D[i][j-1] + 1$: insert the $j$-th letter of $b$.

The base cases are $D[i][0] = i$ (delete all $i$ letters) and $D[0][j] = j$ (insert all $j$ letters). Fill row by row; the answer is $D[m][n]$, the bottom-right cell.

<Steps title="Edit distance from TEA to EAT, by hand">
  <Step title="Base row and column">
    The empty-prefix row is 0, 1, 2, 3 (inserts) and the empty-prefix column is 0, 1, 2, 3 (deletes).
  </Step>
  <Step title="Row T (first letter of TEA)">
    T vs E differ: $\min(0 + 1,\ 1 + 1,\ 1 + 1) = 1$. T vs A differ: $\min(1 + 1,\ 2 + 1,\ 1 + 1) = 2$. T vs T match: up-left is 2, plus $c = 0$, gives 2. Row: 1, 2, 2.
  </Step>
  <Step title="Row E">
    E vs E match: up-left is 1, so 1. E vs A differ: $\min(1 + 1,\ 2 + 1,\ 1 + 1) = 2$. E vs T differ: $\min(2 + 1,\ 2 + 1,\ 2 + 1) = 3$. Row: 1, 2, 3.
  </Step>
  <Step title="Row A">
    A vs E differ: $\min(2 + 1,\ 1 + 1,\ 3 + 1) = 2$. A vs A match: up-left is 1, so 1. A vs T differ: $\min(2 + 1,\ 3 + 1,\ 1 + 1) = 2$. Row: 2, 1, 2.
  </Step>
  <Step title="Read the answer">
    The bottom-right cell is **2**: delete the T at the front and insert a T at the end. (Three substitutions would also work, but cost 3.)
  </Step>
</Steps>

The table has $(m + 1)(n + 1)$ cells and each takes $O(1)$ work, so edit distance is $O(mn)$ time and space. Trying every possible sequence of edits instead would be exponential.

<Note title="Backpropagation is dynamic programming">

When a neural network computes its gradients, it stores each layer's result on the forward pass and reuses it on the backward pass, instead of recomputing the same chain-rule products for every weight. That is exactly the DP idea, and it is why training costs only a small multiple of a forward pass.

</Note>

## Graphs: breadth-first and depth-first search

A <Term def="A set of nodes (also called vertices) joined by edges. Maps, social networks, the web and neural network computations are all graphs.">graph</Term> is a set of **nodes** (places, people, web pages) joined by **edges** (paths, friendships, links). Two nodes joined by an edge are **neighbours**. In Python a graph is usually stored as an <Term def="A dict mapping each node to the list of its neighbours.">adjacency list</Term>: a dict from each node to the list of its neighbours.

<Analogy title="Searching a shopping mall for a friend">

You can search floor by floor: check every shop on level 1, then every shop on level 2, and so on. That is **breadth-first**. Or you can follow one corridor to its very end, then come back to the last junction and try the next corridor. That is **depth-first**.

</Analogy>

- <Term def="Breadth-first search: explore a graph level by level using a queue, visiting all nodes 1 edge away, then 2 edges away, and so on.">BFS</Term> keeps the nodes waiting to be visited in a <Term def="A first-in, first-out (FIFO) line: items are added at the back and taken from the front. Python's collections.deque does both in O(1).">queue</Term> (first in, first out). It visits everything 1 edge from the start, then everything 2 edges away, and so on, so the first time it reaches the goal it has used the **fewest edges**: BFS finds shortest paths in graphs where every edge counts the same.
- <Term def="Depth-first search: follow one path as deep as possible, then back up to the most recent choice and try the next option. Uses a stack or recursion.">DFS</Term> keeps them on a <Term def="A last-in, first-out (LIFO) pile: the item added most recently is taken first. A Python list with append() and pop() is a stack.">stack</Term> (last in, first out), or simply uses recursion (the call stack). It follows one route as deep as it can, then backs up to the latest junction. It finds *a* path, often not the shortest.

<GraphTraversal />

<Steps title="BFS from Home to Hawker, by hand">
  <Step title="Start">
    Queue: [Home]. Mark Home as seen.
  </Step>
  <Step title="Visit Home">
    Its neighbours MRT and Park are new: record Home as their parent and add them. Queue: [MRT, Park].
  </Step>
  <Step title="Visit MRT, then Park">
    MRT adds School and Mall. Park's neighbour Mall is already seen, so Park only adds Hawker (parent Park). Queue: [School, Mall, Hawker].
  </Step>
  <Step title="Visit School, then Mall">
    School adds Library, Mall adds Clinic. Queue: [Hawker, Library, Clinic].
  </Step>
  <Step title="Visit Hawker: the goal">
    Walk back through the parents: Hawker ← Park ← Home. The path Home → Park → Hawker has 2 edges, the fewest possible.
  </Step>
</Steps>

Both searches look at each node once and each edge once (twice, once from each end, in an undirected graph), so both take $O(V + E)$ time for $V$ nodes and $E$ edges. The essential difference is which end of the frontier you take from: the oldest item (a queue, BFS) or the newest (a stack, DFS). In code there is one more detail: a stack-based DFS must mark a node as visited when it is **popped**, not when it is pushed, so just swapping `popleft()` for `pop()` in `bfs_path` does not give a true DFS. A recursive DFS gets this right automatically.

### Graphs in AI

Graphs are everywhere in AI. When PyTorch runs your model it builds a **computational graph**: each node is an operation, and each edge says which result feeds into which. Backpropagation walks this graph backwards.

<PastPaperQuestion paper="prelim2026" n={43} />

Language models also search. **Beam search** builds sentences word by word like a BFS over all possible sentences, but keeps only the $k$ best partial sentences at each level (a top-$k$ selection, as in the last lesson), because the full tree of sentences grows exponentially.

<PastPaperQuestion paper="noai2025" n={18} />

For weighted graphs, where edges have different costs (minutes of travel, fares), BFS no longer guarantees the cheapest path; algorithms such as Dijkstra's and A\* extend the same frontier idea with a priority queue (a heap). They are the next step in classical AI search and planning: not required by the IOAI syllabus, but worth knowing by name.

Match the words fast: **base case** stops recursion; **overlapping subproblems** means memoise or use DP; **queue** means BFS and shortest paths (fewest edges); **stack or recursion** means DFS; both searches are $O(V + E)$. To trace a recursive function, write each call on its own line, indented, and fill in the return values on the way back up, exactly like the factorial trace above.

</ExamTip>

<Takeaways>

- A recursive function needs a base case and a recursive case that moves towards it; each waiting call sits on the call stack, so depth $n$ costs $O(n)$ space.
- Naive recursive Fibonacci is exponential because it solves the same subproblems again and again; memoisation stores each answer once and makes it $O(n)$.
- Dynamic programming fills a table of subproblem answers in an order where each entry depends only on entries already filled; edit distance takes $O(mn)$.
- BFS (queue) explores level by level and finds fewest-edge paths; DFS (stack or recursion) dives deep and backtracks; both are $O(V + E)$.

</Takeaways>
